# ARIS — проектный менеджер TELOS SPACE и MCP

ARIS (Арис) — проектный менеджер TELOS SPACE. Он работает с локальными пользователями, их задачами, досками и доступными проектами. Общие проектные знания описаны в [knowledge.md](knowledge.md). Настройки и их значения — в [backend/.env.example](../backend/.env.example) и [settings.py](../backend/src/core/settings.py).

## Интерфейсы и границы данных

- Единственная проектная вкладка `/projects/:key/chat` объединяет командную переписку и обращение «Арис, …». Приватные проектные диалоги доступны на `/projects/:key/conversations` через [ProjectConversationWorkspace](../frontend/src/components/agent/ProjectConversationWorkspace.tsx), знания — на `/projects/:key/knowledge`. Обе страницы открываются из меню на `/chat`; знания не загружают приватные диалоги.
- [Общее окно чатов](../frontend/src/components/chat/FloatingChatDock.tsx) с личным диалогом Ариса доступно на разных экранах. Проверенный контекст страницы определяет проект, задачу, доску и выделенные объекты; этот контекст сам по себе не даёт прав.
- В общем чате проекта обращение «Арис, …» запускает ответ для всей команды. Режим `project_chat` ограничен этим проектом; личные режимы `widget_project` и `widget_personal` описаны в [aris.py](../backend/src/agent/aris.py).
- Внешний клиент использует REST `POST /api/v1/aris/requests`, `GET /api/v1/aris/requests/{request_id}` или MCP `telos_ask_aris` / `telos_get_aris_result`.

Имя в интерфейсе — ARIS (Арис), в ответах и системной инструкции — «Арис, проектный менеджер» с мужским родом. Обращения «Арис, …» и «ARIS, …» распознаются в начале сообщения без учёта регистра, на границе имени; «Аристотель», «Арисон» и имя внутри фразы не вызывают помощника. Runtime и интерфейс используют имена `Aris*`; пользовательские сообщения, приватная история и идентификаторы записей сохраняются.

Проект, инициатор и область записи задаются сервером. Проверяются активность пользователя, доступ к объекту и владелец диалога. Личная переписка и память не становятся общими фактами проекта. Внешние запросы дополнительно изолированы по владельцу и ID ключа.

## Исполнение и инструменты

[ProjectAgentService](../backend/src/services/project_agent.py) собирает актуальные данные и запускает [ArisRuntime](../backend/src/agent/runtime.py) на PydanticAI. [AgentRoutingService](../backend/src/services/agent_routing.py) выбирает доступный проект либо личную область. OpenAI-совместимая модель настраивается через `AGENT_MODEL`, `LLM_API_KEY`, `LLM_API_BASE_URL` или `LLM_API_URL`; адаптер — [agent_model.py](../backend/src/clients/agent_model.py).

Runtime использует PydanticAI 2.59.0 (`pydantic-ai-slim[openai]`) и совместимый OpenAI SDK 3.26.0. Фильтрация инструментов и сокращение истории подключены через capabilities `PrepareTools` и `ProcessHistory`; инструменты создаются публичным `Tool.from_schema`. Явная стратегия `exhaustive` выполняет допустимые действия, даже если модель одновременно вернула итоговый ответ. Экспорт телеметрии отключён, в том числе при глобальном `Agent.instrument_all()`.

Постоянная инструкция содержит личность Ариса, стиль и общие границы. Подробные
правила и схемы разделены на 13 предметных наборов в
[capabilities.py](../backend/src/agent/capabilities.py). Нативный PydanticAI
`Capability(defer_loading=True)` сначала показывает короткий каталог и
`telos_load_capability`; выбранные инструкции и инструменты появляются после загрузки.
Простой разговор может завершиться одним модельным запросом. Отдельного
последовательного классификатора для выбора набора нет. Каталог фильтруется
по режиму и scopes до передачи модели; состояние загрузки действует один ответ.
SQL-контекст читается при загрузке первого набора, embeddings/Qdrant — только
для знаний, документов и итоговых отчётов.

Текущий каталог и признаки записи, подтверждения, режима и прав владельца находятся в [action_catalog.py](../backend/src/agent/action_catalog.py), схемы аргументов — в [project_tool_inputs.py](../backend/src/schemas/project_tool_inputs.py). Сборка проектных, личных и knowledge-инструментов — в [dependencies/services.py](../backend/src/dependencies/services.py). В этот же путь включены ИСР/WBS, доски и отчёты задач; отдельного каталога в документации нет.

`AgentToolExecutor` принимает только зарегистрированные инструменты и валидированные аргументы. Модель получает доступные схемы; `telos_get_tool_schemas` позволяет раскрыть точные параметры. Доменные операции выполняются через [AgentActionsService](../backend/src/services/agent_actions.py), а не произвольные SQL, методы или URL из ответа модели.

`WriteGate` создаётся перед первым допустимым изменяющим вызовом и проверяет,
поручил ли пользователь изменение. Приветствия и чтение его не запускают;
изменяющий инструмент ждёт положительного решения. Отказ или ошибка
классификации закрывают запись. Gate не заменяет проверок доступа, scope,
версии объекта и подтверждения конкретного действия.

Во внешнем `agent:ask` поле `text` задаёт вопрос, а дословное `user_text` служит основанием для изменений. Без `user_text` разрешено только чтение. `agent:ask` открывает чтение в пределах доступа владельца; дополнительные scopes ограничивают запись. Для прямых REST/MCP-чтений действуют их собственные scopes. Соответствие действий правам — в [action_scopes.py](../backend/src/agent/action_scopes.py).

## Очередь, повтор и транзакции

[AgentConversationsService](../backend/src/services/agent_conversations.py) хранит диалоги и задания виджета, проектного интерфейса и внешнего API; [ArisChatService](../backend/src/services/aris_chat.py) обслуживает общий чат. Их исполняет один [AgentWorker](../backend/src/agent/worker.py), собранный в DI. Он работает и при `KNOWLEDGE_ENABLED=false`.

Вопрос и заготовка ответа сохраняются до вызова модели. Ответ проходит `queued → processing → completed/failed`. Захват очереди использует блокировки PostgreSQL; `run_id` защищает от завершения и записи устаревшей попытки. Истёкшее или прерванное выполнение становится ошибкой, которую пользователь может повторить. Закрытие браузера не отменяет сохранённое задание.

В общем чате страница сообщений и состояния ходов читаются отдельными запросами.
Если ход уже `completed/failed`, а строка ответа ещё является заглушкой первой
ревизии, presenter перечитывает её с обновлением ORM identity map. Это устраняет
гонку при READ COMMITTED: конечный статус не показывается со старым пустым ответом.
Допустимый итоговый ответ только карточкой сохраняется.

Стабильный UUID `request_id` защищает отправку от сетевого дубля: тот же запрос возвращает прежний результат, несовместимое содержимое получает конфликт. В личном диалоге допускается один незавершённый ответ. Контракты HTTP — в [aris.py](../backend/src/api/v1/endpoints/aris.py), [agent_conversations.py](../backend/src/api/v1/endpoints/agent_conversations.py) и [agent_requests.py](../backend/src/api/v1/endpoints/agent_requests.py).

У внутреннего действия без явно переданного `request_id` квитанция находится по
ходу/реплике, пользователю, проекту, каноническому имени и нормализованным аргументам.
Проверка актуальных прав и блокировка выполняются до поиска. При повторе берётся
сохранённый UUID; новая операция получает идентификатор с нейтральным namespace.
Заготовка ответа общего чата создаётся вместе с вопросом одной транзакцией;
повтор отправки находится по пользовательскому UUID до создания второго ответа.

Идемпотентность отдельного действия обеспечивают ключ вызова, advisory lock и уникальность журнала `agent_tool_runs`. Для повторной MCP-записи нужен тот же UUID и те же аргументы. Изменение домена и успешная квитанция фиксируются одной внешней транзакцией: [AgentToolUnitOfWork](../backend/src/repositories/unit_of_work.py) объединяет вложенные SAVEPOINT. Перед записью проверяются актуальная попытка и доступ. Созданные файлы компенсируются при rollback, удаление существующих откладывается до commit.

DB-соединение освобождается перед LLM, embeddings, Qdrant и ожиданием человека. Файлы, внешние клиенты и короткие DB-области создаются через [dependencies/scopes.py](../backend/src/dependencies/scopes.py).

## Подтверждения

Действия с `requires_confirmation` сохраняют параметры и предварительный результат как `pending`. Интерфейс показывает карточку; модель не может подтвердить её своим аргументом. Перед исполнением повторно проверяются инициатор, текущий доступ, состояние объекта и версия. Новый вопрос отменяет прежние неподтверждённые предложения своего диалога.

Для внешнего API ответ содержит `done`, `pending` и `confirm_url`. `pending` ещё ничего не изменяет. По ссылке `?confirm=<id>` решение принимает сам инициатор в локальной cookie-сессии; API-ключи и токены к этому маршруту не допускаются. POST проверяет источник запроса; стандартный срок решения — 24 часа (`AGENT_ACTION_CONFIRM_TTL_HOURS`). См. [agent_pending.py](../backend/src/api/v1/endpoints/agent_pending.py) и [AgentConfirmModal](../frontend/src/components/agent/AgentConfirmModal.tsx).

Прямой MCP-вызов каталога использует form elicitation: человек видит проект, объект и сохранённые параметры. После ожидания снова проверяются токен и scope. Без поддержки elicitation действие остаётся невыполненным; `cancel` оставляет ожидание, `reject` отклоняет. Продолжение использует прежний `request_id`.

## Файлы и контекст модели

Приватные загрузки хранятся локально под `UPLOADS_PATH/agent`, привязаны к собственному диалогу и отправляются как `file_ids`. Пределы: 10 МБ на файл, пять файлов в вопросе, 20 загрузок в диалоге. `telos_attach_uploaded_file` копирует разрешённые байты в задачу; индексирование такой копии выполняется обычным knowledge-контуром. Локальные пути и произвольные внешние файловые URL не являются аргументами модели. См. [agent_files.py](../backend/src/services/agent_files.py) и [agent_tool_files.py](../backend/src/storage/agent_tool_files.py).

Полная история сохраняется в PostgreSQL. В модель передаются последние
завершённые реплики, ограниченная память и актуальные чтения.
[AgentContextBudget](../backend/src/agent/context.py) сокращает повторы и большие
результаты перед каждым раундом, сохраняя ожидающие подтверждения, последнюю
квитанцию записи и курсоры продолжения. Даты, ID и решения сохраняются точными
фрагментами; пропуски явно помечаются. Текущее поручение хранится отдельно и
не сокращается. Фоновое саммари не задерживает следующий ответ: пока оно
готовится, виджет добавляет ограниченные выдержки ещё не свёрнутой переписки.
Читаются начало и конец отставшей памяти, середина при большом отставании
может быть пропущена. Оценка токенов локальная: UTF-8 байты / 3, поэтому она
не равна usage провайдера. Точные сведения следует дочитывать из оригинального источника.

Единый каталог документов использует `document_ref`: `telos_list_documents`
читает метаданные с фильтрами, `telos_get_document` — ограниченную страницу текста,
остальные действия создают, правят и связывают документ через общий доменный сервис.
Самостоятельных инструментов перечня и удаления вложений нет; загрузки проекта,
задачи и Markdown читаются и удаляются одинаково. Специальные операции переноса
загрузки из диалога и создания текстового оригинала сохраняют существующие имена.
WriteGate и проверка актуального доступа действуют для всех типов документа.

В личном режиме те же действия работают с документами личных задач.
Пустой project context ограничивает SQL-каталог личными источниками до пагинации;
проектный разговор сохраняет точную границу своего проекта. Личные материалы
не попадают в проектную коллекцию Qdrant. MCP/worker передают текущий server-only
Principal в общий сервис; предварительный допуск инструмента не заменяет scopes
владельца документа. Перед записью и повтором проверяются активный пользователь,
актуальный ключ/токен и пересечение с первоначальными правами. Секрет не сохраняется
в сообщениях: worker использует ID и снимок прав, без расширения после постановки
в очередь. Повторная auth-проверка не делает audit commit внутри бизнес-транзакции.

Модель выбирает выданный сервером `fragment_handle`, если документ подтверждает
ответ. Сервер проверяет точную цитату, Unicode-диапазон и хэш представления;
основной источник отмечается в ответе и открывается в правой панели даже при
нескольких документах. Саммари не становится доверенной цитатой. Старый хэш
показывается как изменённый документ без переноса подсветки. Подробный контракт —
[knowledge.md](knowledge.md#проверяемые-фрагменты-ариса).

## MCP и аутентификация

Streamable HTTP доступен на прежнем `/mcp` основного backend и в отдельном приложении [mcp_server/app.py](../backend/src/mcp_server/app.py). Отдельный процесс запускается из `backend` командой `python -m src.mcp_server.worker` (`MCP_HOST`, `MCP_PORT=8021`), Compose — `docker compose --profile mcp up -d mcp`. Для queued `telos_ask_aris` нужен работающий backend с AgentWorker. `/health` и `/health/live` проверяют процесс, `/health/ready` — доступность PostgreSQL.

HTTP и MCP принимают ключи через `Authorization: Bearer`. READ/WRITE-токен имеет формат `telos_token_<secret>`, ключ с выбранными scopes — `telos_key_<8 hex>_<32 hex>`. Публичный `key_prefix` содержит только восемь hex-символов; отображаемый префикс токена — восемь случайных символов после маркера. Ключ действует от владельца; `actor` не позволяет сменить пользователя. Все инструменты MCP и Ариса имеют единственные имена `telos_<действие>_<сущность>`, проверяемые при регистрации. Реестр MCP — [registry.py](../backend/src/mcp_server/registry.py); каталог действий Ариса — [action_catalog.py](../backend/src/agent/action_catalog.py).

`telos_list_project_tools` раскрывает каталог и схемы; `telos_execute_project_tool` исполняет общие действия. Доступ к проекту и ресурсу проверяется при каждом вызове. Инструменты без регистрации прав закрыты для новых ключей. Все scopes заданы в [api_scopes.py](../backend/src/utils/api_scopes.py); управление ключами и токенами доступно только из локальной сессии. Секрет показывается при выпуске один раз, в БД хранится хэш.

Разрешённые MCP hosts/origins задаются `MCP_ALLOWED_HOSTS` / `MCP_ALLOWED_ORIGINS`. [Nginx](../nginx/nginx.conf) сохраняет маршрутизацию `/mcp`, отключает буферизацию и нормализует завершающий слэш. Корпоративных SD/PM-клиентов, staff/корпоративных ролей, flows, учёта времени, remote storage и Phoenix/OTLP/`biocard_health` в контуре нет.

### Диагностика и обновление каталога MCP

`initialize.serverInfo.version` содержит `2.0.0+source.<sha256>` — отпечаток
нормализованных исходников backend и `requirements.txt`. Он одинаков для LF/CRLF
и не зависит от `.env`, ключей и Git checkout. Это идентификатор исходников,
не Git SHA и не идентификатор Docker-образа.

Ответ `tools/list` содержит `_meta["telos-space/catalog"]`: версию формата,
`sha256`, `tool_count`, `build_version`, `mcp_sdk_version`, `scope="response"`
и `complete`. Хеш учитывает схемы входа/выхода, описания, defaults и annotations.
`complete=true` означает ответ без входящего cursor и без `nextCursor`;
при пагинации метаданные относятся только к полученной странице.

Полный каталог сохраняет диагностическая команда из `backend`:

```powershell
.\venv\Scripts\python.exe -m src.mcp_server.catalog_probe local --output "$env:TEMP/telos-mcp-local.json"
.\venv\Scripts\python.exe -m src.mcp_server.catalog_probe remote http://127.0.0.1:8021/mcp/ --token-env TELOS_MCP_API_KEY --output "$env:TEMP/telos-mcp-server.json"
.\venv\Scripts\python.exe -m src.mcp_server.catalog_probe compare "$env:TEMP/telos-mcp-local.json" "$env:TEMP/telos-mcp-server.json"
```

Для основного backend замените адрес отдельного MCP-процесса своим `/mcp`.
Пример читает ключ из уже заданной переменной `TELOS_MCP_API_KEY`.
Снимок и краткий вывод не содержат ключа и адреса
сервера. `local` не читает `.env` и не открывает соединений; `remote` создаёт
новую Streamable HTTP-сессию, проходит все страницы `tools/list` и не вызывает
доменные инструменты. `compare` перечисляет добавленные, удалённые и изменённые
инструменты; коды завершения: 0 — каталоги совпали, 1 — различаются, 2 — ошибка
диагностики. Число инструментов само по себе не определяет актуальность схем.

Каталог приложения фиксируется при запуске процесса. После изменения инструментов
обновите сервер, получите свежий `remote`-снимок и переподключите внешний клиент,
создав новую сессию. Сопоставьте имена, параметры и описания в клиенте со снимком.
Если метаданные поиска агента обрезаны, прочитайте их небольшими группами:
обрезание вывода не означает отсутствие инструмента на сервере.
Автоматическое обновление интерфейса конкретного внешнего клиента проверяется
отдельно; переподключение без нового каталога не подтверждает его актуальность.

В проверенном Streamable HTTP-подключении с протоколом `2025-11-25` сервер
объявляет `tools.listChanged=false`. Статическое приложение не рассылает
`notifications/tools/list_changed` при развёртывании или перезапуске.
Изолированный TCP-тест SDK подтверждает получение явно отправленного
уведомления, сброс клиентского кеша и `list_tools(cache_mode="refresh")`.
Эти проверки относятся к SDK-клиенту; поведение обновления интерфейса Codex
из них не следует. После перезапуска используйте новую сессию.

Ранее открытый контекст Codex может продолжать показывать прежний набор имён
после обновления сервера. Для проверки каталога используйте новый контекст
субагента без наследования истории. Ожидаемые имена, параметры и fingerprint
берутся из свежего серверного снимка, а не из числа инструментов старого контекста.

Проверенный порядок для оркестратора: после обновления сервера передать MCP-работу
новому субагенту с `fork_turns="none"`, сверить доступные ему имена и параметры
с полным `tools/list`, затем выполнять поручение в этом контексте. Это даёт
новому контексту актуальные инструменты, но не обновляет метаданные родителя.
Принудительное обновление прежнего контекста и отдельный перезапуск приложения
Codex этим экспериментом не проверялись. Клиент раскрывает TypeScript-декларации,
поэтому полное равенство клиентской JSON Schema/defaults/outputSchema не заявляется.

После перевыпуска ключа замена User environment не обновляет окружение уже
запущенного фонового app-server Codex. Он может пережить закрытие окна;
новая сессия или история субагента тоже не обновляет переменные процесса.
При `bearer_token_env_var` клиент продолжит отправлять прежний ключ, даже
если в пользовательских переменных Windows уже сохранён новый.

В локальной Windows-конфигурации проверен `http_headers_helper`: PowerShell
читает `TELOS_MCP_API_KEY` через `GetEnvironmentVariable(..., 'User')` и
возвращает JSON с заголовком `Authorization: Bearer ...`. Сам секрет остаётся
в User environment. Одновременный `bearer_token_env_var` нужно убрать:
явно заданный Bearer имеет приоритет над заголовком helper. После изменения
ключа или настройки перезагрузите MCP-подключение. Штатный запрос app-server
`config/mcpServer/reload` применил эту настройку в уже открытой сессии Codex
0.167.0; нативные `telos_list_projects` и `telos_get_project(TELOS)` прошли
без перезапуска фонового процесса. Параметры helper описаны в
[официальной документации MCP](https://learn.chatgpt.com/docs/extend/mcp),
перезагрузка — в [документации app-server](https://learn.chatgpt.com/docs/app-server).

Для автономной проверки через Codex CLI ограничьте дочерний процесс тремя
чтениями: `telos_list_projects`, `telos_get_project`, `telos_get_task`.
Уже разрешённым пользователем чтениям задайте отдельные
`mcp_servers.telos-space.tools.<tool>.approval_mode="approve"`;
при `approval_policy="never"` требующий подтверждения вызов иначе отклоняется
до отправки на сервер. Эти overrides относятся только к дочернему процессу;
права владельца ключа и scopes по-прежнему проверяет приложение. Описание
параметров — в [официальной документации MCP](https://learn.chatgpt.com/docs/extend/mcp).
Три нативных чтения проверяют вызовы клиента; полный действующий каталог
отдельно сравнивают через SDK. Проверки CLI не подтверждают обновление
инструментов уже открытого интерфейса Codex.

При этой сверке обнаружен конкретный предел клиентского TypeScript-представления:
`telos_update_board_shapes.args.updates[].data.points` показан как
`Array<Array<string>>`, хотя серверная JSON Schema задаёт массив числовых пар
через `prefixItems`. Для сложных вложенных полей сверяйтесь с серверным снимком;
внутренний механизм такого преобразования клиента не установлен.

### Создание проекта через MCP

`telos_create_project` работает без контекста существующего проекта. Обязательны
`key`, `name` и UUID `request_id`; для `telos_key_` требуется `projects:write`.
Прежний WRITE-токен сохраняет право создания, READ-токен его не получает.
Владелец определяется сервером по текущему пользователю; неизвестные параметры,
в том числе попытка передать другого владельца, отклоняются.

Паспорт принимает те же поля и проверки, что REST `ProjectCreateSchema`:
`description_sections` (`problem`, `goal`, `expected_result`, `additional`),
`description_md`, `member_usernames`, `stages`, `status`, `color`, `icon`,
`start_date`, `due_date`. Структурированные блоки имеют приоритет перед
`description_md`. Общий сервис создаёт проект, участие владельца с ролью OWNER,
команду, стадии и начальную свободную доску; значения по умолчанию совпадают с REST.

UUID и исходные аргументы нужно сохранить до первой отправки. После потери
ответа повтор возвращает исходный результат; другое действие или паспорт
с тем же UUID дают конфликт. Проект и квитанция `agent_tool_runs` сохраняются
одной транзакцией PostgreSQL, включая конкурентные вызовы и перезапуск процесса.
Квитанция принадлежит пользователю, не исходному проектному контексту;
удаление созданного проекта не освобождает UUID для повторного создания.
После ожидания блокировки заново проверяются учётные данные и scope,
перед возвратом повтора — доступ к созданному проекту.

Ответ содержит `project_key`, название, статус и проверенную `url`.
По этому ключу можно сразу вызвать `telos_get_project(full_text=true)`
и затем `telos_create_task`. Ошибки паспорта, занятый код и неизвестные
участники не оставляют частично созданного проекта.

Пример «создать проект → прочитать паспорт → создать задачу» —
[create-project](mcp-skills/create-project/SKILL.md).

### Последний сохранённый обзор проекта

Арис читает обзор со вкладки «Обзор» действием `telos_get_latest_project_summary`
из набора `reports`. Инструкция требует вызвать его перед ответом о наличии,
доступности или содержимом сохранённого разбора. Для другого проекта в личном
диалоге используется `telos_run_project_action` с этим же именем действия.

В MCP доступен `telos_get_latest_project_summary(project_key)` с правом
`projects:read`; то же действие можно вызвать через `telos_execute_project_tool`
с `name="telos_get_latest_project_summary"` и `arguments={}`. UUID повтора и право
записи не требуются. READ/WRITE-токены `telos_token_` и `telos_key_`-ключи
используют текущие права локального владельца.

Результат: `found`, полный `report` в формате `AnalyticsReportSchema`,
`source_id="analytics_report:<id>"`, `provenance="generated_analysis"` и пояснение.
В `report` входят `created_at`, `created_by`, модель, оценка, находки, достигнутые
результаты, рекомендации, сигналы и границы анализа. Текст не сокращается до
превью. Если обзор ещё не формировался, возвращаются `found=false`,
`report=null` и `source_id=null`; отсутствие обзора не запускает генерацию.

Выбирается только свод указанного проекта: `created_at DESC, id DESC`.
Это общий для команды обзор, независимо от автора генерации; портфельные
отчёты исключены. При каждом чтении перепроверяется актуальный доступ.
HTTP и агент используют общий `AnalyticsReportReader.get_latest`;
создание LLM/HTTP-клиентов и вызов модели для этого не нужны.

Дата обязательна при обсуждении: сохранённый обзор описывает состояние на
момент генерации. Новые факты и изменения после него Арис проверяет другими
инструментами; вывод AI не становится первичным фактом о текущем проекте.

### Полный текст, повторы и версии задач

`telos_get_task` и `telos_get_project` по умолчанию возвращают превью описания до
2000 символов. `full_text=true` возвращает исходный Markdown целиком.
`description_meta` содержит `truncated`, полную `length`, единицу длины
`unicode_code_points` и `read_full` с готовым вызовом для дочитывания.
Комментарии в `telos_list_comments` имеют такие же `body_meta`; полный отдельный
комментарий читается через `telos_get_comment(task_key, comment_id)`. При каждом
чтении проверяются scope, доступ к задаче и принадлежность комментария задаче.
Карточки и комментарии используют единый формат со структурными метаданными.

Для `telos_create_task` и `telos_add_comment` доступен необязательный UUID `request_id`.
Перед первой отправкой создайте ключ, а после потери ответа повторите его вместе
с теми же аргументами. Одинаковый ключ в контексте владельца и проекта возвращает
прежний результат; другое действие или аргументы с этим ключом дают явный конфликт.
При первом исполнении имена стадий и участников разрешаются после проверки
квитанции, поэтому их последующее переименование или удаление не ломает повтор.
Намеренно новое создание требует нового ключа. Без `request_id` сохраняется прежнее
поведение, которое не гарантирует защиту от дублей.

Используется общий журнал `agent_tool_runs`, advisory lock и уникальность БД.
Доменное изменение и квитанция фиксируются одной транзакцией через существующий
`AgentToolUnitOfWork`; перезапуск или новая MCP-сессия не сбрасывает квитанции.
Для этих прямых операций автоматического срока удаления квитанций нет:
они сохраняются до удаления проекта или владельца. Перед возвратом результата
повторно проверяется текущий доступ, включая перенос или удаление задачи.

Карточки HTTP и `telos_get_task` возвращают положительную `revision` общих полей
и назначений задачи. Передавайте её как `expected_revision` в
`PATCH /api/v1/tasks/{id}`, `telos_update_task`, `telos_set_task_dates` или
`telos_set_watchers`. Проверка под блокировкой строки выполняется до изменений,
истории и outbox; устаревшая версия даёт HTTP 409 либо ошибку MCP без записи.
Описание и его версия в MCP берутся из одного снимка данных. Успешная запись
возвращает актуальную версию.

Изменения через общие сервисы, переносы и пакетные операции повышают версию.
Без `expected_revision` выполняется безусловная правка с повышением версии;
проверка устаревшей версии включается передачей этого параметра. Чек-лист и итоговый отчёт
сохраняют отдельные контракты версий. В карточке UI версия фиксируется при
открытии черновика заголовка, описания или дат; конфликт сохраняет черновик
и предлагает перечитать задачу без автоматической повторной записи.

## Бюджеты и проверяемые ограничения

По умолчанию: `AGENT_CONCURRENCY=2` на процесс, `AGENT_POLL_SECONDS=1`, `AGENT_TURN_TIMEOUT_SECONDS=600`, `AGENT_TOOL_ROUNDS=8`, `AGENT_CONTEXT_TOKENS=12000`, `AGENT_HISTORY_TOKENS=1200`, `AGENT_RETRIEVAL_LIMIT=5`, `AGENT_HISTORY_MESSAGES=10`. Внешний ask ждёт до `AGENT_ASK_WAIT_SECONDS=25`, затем возвращает ID и состояние для polling.

На нативную загрузку наборов допускаются ещё два шага, состоящих только из
загрузчиков. Предметный бюджет и предел восьми вызовов за шаг сохраняются;
на финальном шаге загрузчик также скрыт. Метрика `tools_offered` считает
фактически предложенные function-схемы после разрешения видимости, отдельно
от схемы окончательного ответа.

`LLM_TIMEOUT=300` и `LLM_RETRIES=3` задают пределы отдельного клиента; общий deadline очереди может прервать их раньше. Старый синхронный `POST /projects/{id}/knowledge/ask` и другие синхронные AI-операции сохраняются: у `/api/` в nginx нет увеличенного read timeout, поэтому долгий вызов может закончиться proxy timeout. Для новой долгой работы следует использовать очередь, а не увеличивать время ожидания HTTP.

Для модели Ариса отдельно заданы `AGENT_REQUEST_TIMEOUT_SECONDS=30` и
`AGENT_REQUEST_ATTEMPTS=2`: сетевое ожидание одной HTTP-попытки ограничено
30 секундами, допускается один повтор. Параметры одинаковы у native runtime
и structured JSON-клиента. Это предел отдельной попытки, а не всего многошагового
ответа: учитываются несколько вызовов модели и backoff. Повторяется только
HTTP-запрос модели; ход агента и уже выполненные инструменты не перезапускаются.
Незаданные параметры сохраняют прежние `LLM_TIMEOUT`/`LLM_RETRIES`.
Vision использует прежние пределы, embeddings — собственный timeout.

Обычный HTTP 400 от провайдера автоматически не повторяется. Поэтому ошибка
маршрутизации шлюза, пришедшая с этим кодом, завершает вызов даже при
`LLM_RETRIES=3`; повторы SDK предназначены для сети, таймаутов, 429 и серверных
ошибок (есть также коды 408/409 и указание сервера `x-should-retry`).

На Polza 22.10.2026 воспроизведён отдельный сбой: новый большой запрос проходит,
а идентичный повтор возвращает `400 No endpoints found`. Это повторено прямым
HTTP без PydanticAI для 3.7 Flash и 3.5 Flash-Lite на текущем ключе dashboard.
Изменение префикса или уникальный `prompt_cache_key` восстанавливает ответ;
повтор одного значения метки снова падает. Это указывает на cache routing,
но не устанавливает внутреннюю причину сбоя шлюза.

[request_routing.py](../backend/src/clients/request_routing.py) добавляет уникальную
документированную [метку маршрутизации кэша](https://polza.ai/docs/api-reference/chat/completions)
для каждого модельного вызова Gateway и каждой HTTP-попытки JSON-клиента.
Метка не является API-ключом и не содержит ID пользователя или проекта.
Применение ограничено точным hostname `polza.ai`; модель, промпт, авторизация
и остальные `extra_body` сохраняются. Внутренние HTTP-повторы SDK используют
тело исходного модельного вызова; прежняя retry-политика не менялась.
Повторы целого действия не добавлены. Влияние маршрутизации на попадания
в provider cache следует оценивать по usage, а не обещать прежний cache hit rate.

### Разделение моделей

Сейчас `AGENT_MODEL` задаёт основной PydanticAI runtime и общий structured
`LlmClient`, включая WriteIntent, router и память. Объявленный `LLM_MODEL`
не переключает эти вызовы. `VISION_MODEL` и embeddings настраиваются отдельно.
Активный профиль проекта — `openai/gpt-6-luna` через Polza Standard:
`AGENT_PROVIDER=openai`, `AGENT_REASONING_ENABLED=false`,
`AGENT_REASONING_EFFORT=none`. Он закрепляет обычный OpenAI без fallback;
`none` нужен для function calling Luna через Chat Completions.
Для последующего разделения подходят независимые настройки служебных ролей:
Flash-Lite для коротких классификаций и фонового саммари, основная модель —
для планирования, анализа и выполнения инструментов. Это требует отдельной
проверки качества, особенно допуска записи; отдельные служебные модели не выделены.

Для воспроизводимого сравнения через Polza доступны необязательные
`AGENT_PROVIDER`, `AGENT_REASONING_ENABLED` и `AGENT_REASONING_EFFORT`.
Они одинаково применяются к PydanticAI runtime и общему JSON-клиенту;
vision и embeddings сохраняют собственные настройки. Незаданные параметры
не меняют прежний запрос. Явный `AGENT_PROVIDER` закрепляет маршрут и отключает
fallback; это позволяет сравнивать обычный `openai` отдельно от `openai/flex`.
`AGENT_REASONING_ENABLED=false` выключает thinking, `AGENT_REASONING_EFFORT=none`
передаёт соответствующий уровень в унифицированном объекте Polza `reasoning`.

Основные проверки контрактов: [runtime/WriteGate](../backend/tests/unit/knowledge/test_aris_runtime.py), [MCP scopes и подтверждения](../backend/tests/unit/mcp_server/test_personal_mcp_contract.py), [сквозной PostgreSQL smoke](../backend/tests/integration/repositories/test_personal_workspace_smoke.py). Эти проверки с контролируемой моделью не заменяют оценку качества live LLM.

После изменяющего инструмента каталог обновляется до регистрации его текущего
результата: новая сущность сразу получает проверенный `source_handle` для
следующего шага модели. Финальная проверка актуального каталога сохраняется.
Пустой текст с карточками допустим. Если выбранных sources нет, но текущий
запуск получил серверную квитанцию `completed`, сервис сообщает о выполненном
действии; прошлые квитанции, чтение и `pending` таким подтверждением не считаются.

Короткое «как дела?» без предметного вопроса не загружает проектную сводку;
смешанное сообщение с поручением сохраняет выполнение поручения. Содержательный
ответ о задаче включает её проверенный ключ, простой показ может остаться карточкой.
Общие правила фактов раскрываются вместе с предметными инструментами: пустые
описания не дополняются текстом соседних задач, рекомендации явно отделяются от
данных, стадия «Готово» не доказывает качество результата или отсутствие рисков.
При подсчётах завершённость определяется серверным статусом/is_done_stage. Прямая
правка точной даты одной задачи идёт через `tasks/telos_update_task`; календарное preview
предназначено для перепланирования и зависимостей или явного запроса предварительного просмотра.

## Повторяемый замер живых ответов

[aris_benchmark.py](../backend/scripts/aris_benchmark.py) отправляет 14 фиксированных
сценариев через API виджета, настоящую очередь и настроенный LLM. Измеряется
режим `widget_project`; единый проектный чат использует отдельный режим
`project_chat`, его поведение и задержку отображения в браузере проверяют отдельно.
Набор включает small talk с двумя повторами, чтение и просроченные задачи, создание, приветствие
с переносом срока, подробный отчёт и продолжение диалога после него. Удаление
проверяется только до карточки подтверждения; подтверждение скрипт не отправляет.

Из PowerShell в корне работающего Compose-проекта:

```powershell
Get-Content backend/scripts/aris_benchmark.py -Raw |
  docker compose exec -T backend python - --output /tmp/aris-before.json --label before
docker cp project_dashboard_backend:/tmp/aris-before.json "$env:TEMP/aris-before.json"
```

Это платные вызовы настроенных LLM и embeddings. Скрипт создаёт собственные
синтетические пользователя и проект `TELOSEVAL`, ждёт индексации и удаляет их через
обычный API после прогона. При исключении сохраняет fixture для проверки;
повторный запуск при существующем fixture прекращается без его перезаписи.
Исторические suite IDs `vera-widget-v1` и `vera-project-chat-v1`
и изоляционные маркеры `vera_eval*` / `VERA_EVAL_*` сохранены для
совместимости замеров и безопасной очистки временного окружения.
Ошибки ответов фиксируются без остановки остальных независимых сценариев;
зависимые реплики после ошибки в своём диалоге пропускаются.
Перед ручной очисткой нужно проверить отсутствие
активного задания и принадлежность fixture этому запуску.

`--as-of` должна совпадать с текущей датой backend: старая дата меняет
множество просроченных задач относительно настоящих часов сервера и
отклоняется до создания fixture. Сравнение выполняют в один день.
Для сравнения повторяются те же prompts, `--as-of` и ресурсные лимиты; JSON
содержит hash набора, версии, ответы, квитанции и снимки задач. Время `e2e_ms`
измеряется от отправки до получения конечного ответа с polling каждые 250 мс;
это не время первого токена. Ошибки учитываются отдельно от скорости успешных
ответов. Автопроверки фактов и изменений дополняются чтением ответов по rubric
в JSON; два повтора small talk дают ориентир, а не надёжную оценку p95.
Флаги `read` для ключа, стадии, заголовка и срока проверяют текст ответа;
верная карточка при пропуске ключа в тексте отмечается отдельно при ручной
оценке. Число успешных автофлагов не заменяет проверку содержания отчёта.
Результаты хранятся вне репозитория и не содержат cookie или токенов.
Токены, число предложенных схем и выполненные инструменты берутся из события
`project_agent.ask` по ID тестового проекта и времени конкретной реплики.
При аварии runtime usage может отсутствовать: это не означает отсутствие действий;
для записи источником проверки остаются квитанции и снимки данных.

[aris_model_preflight.py](../backend/scripts/aris_model_preflight.py) проверяет
пять согласованных конфигураций (контрольная Gemini, Qwen3.8 с thinking и без него,
Qwen3.5 без thinking, Luna Standard без reasoning). Используются настоящий
JSON-клиент и runtime с отложенной загрузкой tools; данные синтетические,
БД и изменяющие инструменты не нужны. Запуск из `backend` требует явного
`--live` и нового внешнего пути `--output`; `--profile` ограничивает набор.
У Luna проверка маршрута строгая по всем HTTP-попыткам. Если попытка прервана
сетевым timeout и её provider неизвестен, итоговый preflight останется `failed`
даже при успешных `json_valid`/`native_tools_valid` после повтора. Стоимость такой
попытки остаётся неизвестной; её нельзя считать нулевой или выдавать весь аудит
за полностью пройденный.

[aris_model_compare.py](../backend/scripts/aris_model_compare.py) запускает
сквозной benchmark в отдельных временных PostgreSQL, Redis и Qdrant с портами
только на loopback. Существующие данные/тома и `.env` не изменяются. Каждый
профиль получает новый backend-процесс, пустую БД с настоящими миграциями и
отдельный префикс Qdrant. Backend, worker и benchmark используют одну
конфигурацию. Полный прогон допускается только при совпадении модели и
параметров с успешным `--preflight`; можно передать несколько артефактов и
выбрать прошедшие профили через повторяемый `--profile`.
Историческое имя `gemini-current` сохранено; модель этого контрольного профиля
закреплена на `google/gemini-3.7-flash` и не меняется вслед за активной моделью.
`--repeat` задаёт число повторов (1–3), `--output-dir` — новый внешний каталог.
`--channel project_chat` отдельно проверяет приветствие и чтение задачи через
REST общего чата, настоящую очередь `chat_agent_turns` и привязку ответа к
сообщению участника. По умолчанию используется полный `widget_project`.
При техническом сбое временный stack сохраняется для разбора; его ID находятся
в `round.json`. При штатном завершении удаляются только созданные им контейнеры.

[aris_usage.py](../backend/scripts/aris_usage.py) записывает usage всех
HTTP-попыток общего AI-клиента: runtime, JSON, embeddings, фоновые вызовы и
повторы. Стоимость берётся из `usage.cost_rub`, включая уже включённые в неё
reasoning и cache; отдельно повторно они не начисляются. Неизвестная стоимость
не считается нулём. Маршрут подтверждается после замера через историю только
собственных generation IDs, поскольку обычный ответ Polza может не содержать
`provider`. Заголовки авторизации, промпты и данные аккаунта не сохраняются.
Автопроверка наличия ответа учитывает допустимые карточки источников/действий;
проверки фактических изменений и подтверждений при этом остаются обязательными.
