# План улучшения MCP после первого реального кейса

Первый кейс: **6 ноября 2026 года**. Последняя сверка: **7 ноября 2026 года**.
Статус: **пункты 1, 3 и 4 реализованы локально; HTTPS отложен по решению пользователя**.
Пункты 5–7 остаются планом. Состояние контрактов описано в [Арис и MCP](agent.md).
Изменения не развёрнуты на действующем сервере.

Итоговая проверка реализации 07.11: **1288 backend passed без пропусков**,
включая PostgreSQL, миграции и настоящий MCP Streamable HTTP с синтетическими
ключами; **901 frontend passed, 2 skipped**, ещё **10** проверок после обновления
каталога. Ruff, ESLint, TypeScript/build, генератор каталога и diff-check passed.
UI проверялся компонентными тестами с управляемым API, живые модели не вызывались.

## Контекст и границы выводов

Внешний клиент Codex через настоящий `/mcp` работал с проектом BKS Term
(`TERM`): прочитал проекты и задачи, создал `TERM-2` по Claude Code,
уточнил её описание и добавил комментарий о частичной готовности в `TERM-1`
по Codex. Сохранение проверялось повторным чтением. Автор комментария
определялся сервером; ссылки и ключи задач возвращались в ответах.

Это проверка конкретного пользовательского сценария, а не полный аудит
безопасности, производительности или всех 67 инструментов. Значения ключей,
заголовки авторизации и приватные данные в документ не включены.

| У комментариев и истории есть `limit` до 200, но нет продолжения | Полное чтение длинной истории через эти инструменты требует развития контракта |

Два наблюдения не относятся к дефектам сервера:

- Первое чтение `tools/list` упало во временном клиенте: он пытался разобрать
  SSE-строку после первых 64 КиБ. Компактный JSON каталога занимает около
  105 КиБ. После чтения полного SSE-события ответы успешно разбирались.
  Нельзя обрезать протокольный JSON ради обхода ограничения такого клиента.
- Изменения стадий задач в истории отмечены без API-ключа; клиент инструменты
  перемещения не вызывал. Оснований считать это побочным эффектом MCP нет.
  Отсутствие переменной ключа в окружении уже запущенного клиента также
  не является дефектом серверной авторизации.

## Порядок реализации

### 1. P1 — полное и проверяемое чтение текста

Реализовано: необязательный `full_text` у `tt_get_task` и `tt_get_project`,
`tt_get_comment(task_key, comment_id)`, структурные `description_meta`/`body_meta`.
Прежние имена по умолчанию сохраняют прежние ответы. Длина измеряется в
Unicode code points; полный текст возвращается одним вызовом без обрезания.

Точки входа: [presenters.py](../backend/src/mcp_server/presenters.py),
[server.py](../backend/src/mcp_server/server.py),
[project_query.py](../backend/src/services/project_query.py).

- Сохранить компактные списки, но явно отличить превью от полного текста.
  Отразить реальное поведение в описаниях инструментов.
- Добавить совместимый способ получить полное описание задачи и полный
  комментарий: отдельный инструмент или необязательный режим существующего.
  Не ограничиваться увеличением постоянного лимита.
- Для превью возвращать структурные признаки: факт обрезания, полную длину
  и способ дочитать. Не определять обрезание по суффиксу внутри текста.
- Если используется чтение частями, определить единицу смещения, порядок
  продолжения и ревизию источника; не склеивать части разных редакций.

**Приёмка:** точное чтение Unicode/Markdown длиннее 2000 символов, проверка
последнего условия документа, отсутствие изменения хранения или исходного
текста. Полный текст можно сверить после создания без его сокращения.
Права проекта и scopes проверяются и при дочитывании.

### 2. P1 — HTTPS для внешнего доступа (отложено)

Переход на домен и изменение развёртывания исключены из текущего поручения.

Точки входа: [README](../README.md), [nginx](../nginx),
[production Compose](../docker-compose.prod.yml),
[настройки](../backend/src/core/settings.py).

- Подготовить внешний TLS-адрес и сертификат. Клиенты должны сразу обращаться
  к HTTPS, не отправляя Bearer-ключ сначала на HTTP в надежде на перенаправление.
- Согласовать `APP_PUBLIC_URL`, ссылки задач, cookie, CORS и проксирование
  `/api`, `/mcp` и WebSocket. Учесть сроки действия сертификата и восстановление.
- Сохранить существующие данные, пользователей, ключи и изоляцию окружений.
  Текущий HTTP-сценарий зафиксирован в документации; его замена — отдельное
  изменение развёртывания, а не побочный эффект правки MCP-инструмента.

**Приёмка:** настоящий MCP-клиент выполняет сценарий через HTTPS; HTTP API,
UI и WebSocket продолжают работать. Обновлённая инструкция подключения
не требует передачи ключа по открытому внешнему HTTP.

### 3. P1 — повторы создания задачи и комментария

Реализовано: необязательный UUID `request_id` у прямых инструментов создания
задачи и комментария с общей квитанцией `agent_tool_runs` и `AgentToolUnitOfWork`.
Тот же ключ в основном и прежнем имени относится к одной операции; конфликт
аргументов явный. Квитанции без автоматического TTL переживают перезапуск;
перед возвратом результата проверяется текущий доступ, включая перенос задачи.
Вызов без ключа сохраняет прежнее поведение без защиты от дублей.

Точки входа: [write_tools.py](../backend/src/mcp_server/write_tools.py),
[tasks.py](../backend/src/services/tasks.py),
[task_comments.py](../backend/src/services/task_comments.py).

- Добавить совместимый ключ повтора для создания задачи и комментария.
  Перед реализацией сверить существующие квитанции runtime и досок;
  повторно использовать подходящий общий механизм.
- Один и тот же ключ с теми же аргументами возвращает прежний результат.
  Тот же ключ с другими аргументами даёт явный конфликт.
- Связать квитанцию с владельцем, операцией и целевым контекстом; каждый
  повтор заново проверяет актуальный доступ. Решить срок хранения квитанций.
- Гарантировать защиту от одновременных повторов и перезапуска процесса
  транзакцией и ограничениями БД, а не только памятью HTTP/MCP-сессии.
- Сохранять единые доменные сервисы для HTTP, MCP и Ариса, не обходя WriteGate.

**Приёмка:** потеря ответа после успешной записи, повтор в новой сессии,
два одновременных запроса и перезапуск не создают дубликат. Потеря доступа
не позволяет получить прежний приватный результат через квитанцию.

### 4. P2 — защита полей задачи от параллельного изменения

Реализовано: общая положительная `revision`, необязательная `expected_revision`
для PATCH задачи и MCP-изменений полей, дат и наблюдателей. Общий сервис
проверяет версию под блокировкой до эффектов; прочитанный текст и его версия
относятся к одному снимку. UI фиксирует версию при открытии черновика и
сохраняет его при конфликте. Прежние клиенты продолжают писать без проверки
версии; чек-лист и итоговый отчёт сохраняют свои отдельные контракты.
Миграция `f42b8d0e315a` продолжает `e31a7c9d204f`; действующая БД не обновлялась.

Точки входа: [tasks.py](../backend/src/services/tasks.py),
[task_descriptions.py](../backend/src/services/task_descriptions.py),
[MCP](../backend/src/mcp_server/server.py).

- Сверить существующие ревизии чек-листов, отчётов, чатов и досок.
  Не заменять их и не объявлять весь продукт незащищённым.
- Добавить согласованный контракт ревизии для изменяемых общих полей задачи
  и описания; возвращать ревизию при чтении и успешной записи.
- Определить `expected_revision` и поведение прежних клиентов без него.
  Конфликт должен предлагать перечитать задачу, а не затирать чужую правку.

**Приёмка:** два клиента читают одну редакцию; после первой записи вторая
устаревшая запись отклоняется. Отдельно проверить изменения разных полей
через UI и MCP и сохранение прежнего публичного контракта.

### 5. P2 — компактный каталог с сохранением совместимости

Точки входа: [registry.py](../backend/src/mcp_server/registry.py),
[app.py](../backend/src/mcp_server/app.py),
[integration_docs.py](../backend/src/integration_docs.py).

- Основными оставить имена `tt_`: префикс защищает от коллизий с другими
  MCP-серверами. Прежние короткие имена не удалять.
- Предложить явный компактный профиль каталога без прежних алиасов;
  существующий `/mcp` и старые клиенты сохраняют согласованное поведение.
- При необходимости разделить предлагаемые наборы по сценариям: задачи,
  знания, доски. Ограничение каталога не подменяет серверные scopes.
- Измерить размер каталога и корректность выбора инструмента до и после;
  не считать разбиение на страницы автоматическим сокращением контекста.

**Приёмка:** все основные операции доступны без дублей в компактном режиме;
полный режим сохраняет прежние имена и совместимые схемы. На 7 ноября после
добавления полного чтения и инструмента последнего сохранённого обзора каталог
содержит 45 основных и 24 прежних имени.
Старые READ/WRITE-токены,
`ttk_`-ключи и адрес `/mcp` продолжают работать.

### 6. P2 — схемы результатов и метаданные поведения

Точки входа: [registry.py](../backend/src/mcp_server/registry.py),
[presenters.py](../backend/src/mcp_server/presenters.py),
[integration_docs.py](../backend/src/integration_docs.py).

- Ввести типизированные модели результатов для чтения и записи, включая
  ошибки, продолжение, обрезание текста и квитанции.
- Добавить корректные `readOnlyHint`, `destructiveHint`, `idempotentHint`:
  не помечать создание идемпотентным без реальной гарантии повтора.
- Метаданные помогают клиенту, но не расширяют права и не заменяют
  серверное определение автора и проверку доступа.
- Сохранять совместимость согласованной версии MCP; обновлять сгенерированный
  каталог справки, не редактируя его вручную.

**Приёмка:** `structuredContent` соответствует опубликованной схеме;
ошибку выполнения можно отличить от успешной записи. Прежние алиасы
имеют те же права и доменный результат, что и основные инструменты,
сохраняя намеренные различия прежних форматов ответов.

### 7. P2 — продолжение комментариев и истории

Точки входа: [server.py](../backend/src/mcp_server/server.py),
[project_query.py](../backend/src/services/project_query.py).

- Добавить совместимое продолжение и признаки наличия следующих страниц.
  Определить устойчивый порядок и поведение при новых событиях во время чтения.
- Сохранить лимиты отдельного ответа, доступ к задаче и возможность получить
  полный текст комментария из шага 1.

**Приёмка:** история больше 200 записей читается целиком без пропусков
и дублей; новые записи не ломают обход. Прежний вызов только с `limit`
продолжает работать.

## Общая проверка и завершение

Для каждой реализации выбирать проверки по
[правилам backend](../backend/tests/README.md): unit/API для контракта,
настоящий PostgreSQL для конкурентности, транзакций и квитанций, настоящий
MCP-транспорт для подключения и повторов. Пропущенную интеграционную
проверку не считать успешной. После изменения схем инструментов выполнять
проверку генератора `python -m src.integration_docs --check` и characterization.

Контрольный сценарий: прочитать тестовый проект → создать задачу с длинным
описанием → прочитать его полностью → безопасно повторить запрос после
потери ответа → изменить после проверки ревизии → добавить и перечитать
комментарий → дочитать длинную историю. Повторить для современного ключа
и поддерживаемых прежних клиентов; отдельно проверить отозванный ключ,
недостаточный scope и отсутствие доступа к проекту.

Использовать собственные тестовые данные. Не удалять задачи реального кейса,
не публиковать ключи и не вызывать LLM для проверки обычного CRUD.
Изменение схемы БД требует миграции поверх существующей цепочки и резервной
копии перед обновлением действующей БД. Этот план не выполняет развёртывание,
коммит или push. После реализации актуализировать существующие описания
подсистем и MEMORY; не создавать новые параллельные отчёты этого кейса.
