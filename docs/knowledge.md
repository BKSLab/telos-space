# Знания проекта

Компоновка вкладки «Знания», поведение карты и ленты на разных экранах и
точки входа для доработки описаны в [визуальном контракте вкладки](knowledge-tab-design.md).

PostgreSQL и локальные файлы — первичные данные; Qdrant хранит восстанавливаемый производный индекс. Проект задаёт границу каталога, поиска, связей и коллекции. Доступ проверяется REST/MCP-адаптером и агентом; сведения из другого проекта нельзя получить через ID источника. Исполнение агента описано в [agent.md](agent.md).

## История проекта — TELOS-20

`GET /api/v1/projects/{project_id}/history` доступен участникам проекта.
Для API-ключа нужны `projects:read`, `tasks:read` и `knowledge:read`.
Неучастник получает 404. Запрос читает PostgreSQL.

| `kind` | Источник и покрытие |
|---|---|
| `task_activity` | `task_activity`: сохранённые события, тип, доступные значения до и после, причина и снимок автора. Маркеры добавления комментариев исключены в пользу самих комментариев. События переноса и снятия связей исключены, поскольку могут раскрывать прежний проект. |
| `task_comment` | `task_comments`: существующие комментарии с текущим текстом, исходным временем и снимком имени автора. Удалённые комментарии и прежние версии текста отсутствуют. |
| `task_report` | `task_reports`: каждая опубликованная ревизия со временем и именем публикатора. |
| `project_deadline` | `project_deadline_changes`: сохранённые записи о назначении, изменении или снятии срока проекта. |
| `project_context` | `project_context_history`: записанные версии паспорта с номерами выше 0, изменёнными полями и снимком автора. Версия 0 содержит прежнее исходное состояние с датой фиксации и исключена. |
| `risk_created` | `project_risks`: время создания существующего риска и его текущий заголовок. Таблица хранит ответственного, поэтому `actor_name` равен `null`. Журнала правок и удаления рисков нет. |
| `document_created` | `documents` и `project_files`: время создания или загрузки существующего Markdown-документа либо файла с прямым владельцем-проектом. Заголовок и имя автора по сохранённому ID читаются из текущих данных. Удалённые загрузки, документы задач, вложения и их производные копии исключены. Версия и `updated_at` отражают текущее состояние и не дают отдельных событий правок. |

Лента исключает задачи с сохранённым событием переноса и их комментарии и
отчёты. Эти записи привязаны к задаче, а принадлежность проекту на момент
события отдельно не сохранена. При удалении задачи её записи пропадают вместе с ней.
В ленте также отсутствуют отдельные события создания задач, переименования,
изменения состава команды и правок либо удаления рисков и документов. Для новых
записей таких типов понадобится сохранять проект, автора и время в момент действия.
Таблицы Git содержат технические квитанции доставки (`git_deliveries`),
снимки, текущее состояние изменений (`git_changes`) и связи с задачами.
Чтение Git-содержимого требует проверки upstream-доступа через Git-сервис,
поэтому эти таблицы исключены. Переписка и её кэши также исключены.
Миграций и восстановления пропущенных событий по текущим значениям нет.

`kind` принимает одно из значений таблицы. `q` ищет буквальную подстроку
в заголовке или деталях, `actor` — в имени автора. Оба поиска
регистронезависимые, пустое значение отключает фильтр. Детали ограничены 500
символами. `since` и `until` принимают `YYYY-MM-DD` и включают указанные
календарные дни UTC. Все заданные фильтры применяются одновременно.

Ответ содержит `items` с полями `id`, `kind`, `title`, `detail`,
`created_at` (ISO 8601), `actor_name`, `task_id`, `document_ref` и `next_offset` на уровне
страницы. События сортируются по убыванию времени, при совпадении — по
убыванию строкового `id`. `limit` по умолчанию 20, диапазон 1–100.
`offset` по умолчанию 0. `next_offset: null` обозначает последнюю страницу.
Каждый запрос читает текущие данные. Вставки, правки и удаления между
запросами могут сдвинуть границы страниц.

## Каталог и источники

Единый реестр [knowledge/catalog.py](../backend/src/knowledge/catalog.py) определяет типы источников, принадлежность проекту, разрешённые поля, содержательный текст и исключения. [KnowledgeSourcesRepository](../backend/src/repositories/knowledge_sources.py) строит его из актуального PostgreSQL. При добавлении ORM-таблицы или столбца нужна явная политика: источник, часть другого источника, связь или мотивированное исключение.

| Область | Что доступно |
|---|---|
| Проект и команда | Паспорт, описание, публичная локальная идентичность участников и проектные роли |
| Задачи | Описание, чек-лист, назначения, комментарии, вложения, события и связи |
| Отчёты задач | `task_report`: опубликованный текст ревизии, автор и связь с задачей |
| Документы | Markdown и загруженные оригиналы проекта и задач, сохранённый текст, состояния обработки и связи |
| План проекта | ИСР/WBS, стадии канбана, вехи, зависимости и история срока |
| Риски | Описание, снижение и реагирование, текущие оценки и ответственный |
| Доски | Содержательные проектные стикеры и их связи с задачами |
| Аналитика | Сохранённый проектный AI-свод с отметкой исторического вывода |

Точный набор `SourceType`, `POLICIES`, `EXCLUDED_TABLES`, `EXCLUDED_FIELDS` поддерживается в коде. Чек-лист входит в задачу, строки связей образуют граф без отдельных embeddings. Геометрия фигур и сцены досок читаются доменными инструментами; наличие их в UI не означает отдельного semantic source.

Личные задачи и доски без `project_id` не попадают в общие знания проекта; для них существуют личные инструменты Ариса. Чаты, диалоги агента, память, очередь, квитанции действий и приватные загрузки не индексируются. Отправленный в чат файл становится проектным источником после явного прикрепления к задаче. Пароли, токены, секреты подписок и личные контакты исключены. Корпоративных SD/PM-источников, staff, flows, time tracking и remote storage нет.

Файлы переписки имеют отдельный PostgreSQL-кэш `chat_file_texts`: подготовка
начинается при загрузке приватного draft, не дожидаясь Send. Кэш не создаёт
проектный knowledge source, embeddings или точки Qdrant. До публикации ни текст,
ни метаданные draft не доступны инструментам Ариса; после Send чтение ограничено
текущей перепиской, доступной историей и свежим ACL. В общий чат не попадают
материалы личного или приватного проектного диалога. Оригинал сохраняется отдельно
и не обрезается при достижении предела кэша; `truncated` обозначает именно
ограничение извлечённого текста. Файлы входят только в `attachments` конкретной
реплики внутри `chat_context`: текущий вопрос, 15 предыдущих подходящих
сообщений и отдельно старый адресат ответа. Историю дочитывают по теме, автору,
датам и курсорам через `telos_list_chat_messages` / `telos_get_chat_message`,
затем текст выбранного файла — через `telos_read_chat_file`. Ни перечень
сообщений, ни начальный контекст не запускают OCR старых файлов без кэша.
Legacy-файл ставится в очередь при явном чтении. Lifecycle и пределы — в
[контракте файлов](agent.md#файлы-и-контекст-модели).

Цитаты переписки — отдельные `message_references`, не knowledge `SourceType`,
`sources`, embeddings или точки Qdrant. Сервер выдаёт nonce-handle прочитанного
сообщения, сверяет текущие ACL, revision, hash и точную Unicode-цитату перед
публикацией, затем проверяет состояние при чтении сохранённого ответа.
Изменённый или удалённый источник не раскрывает прежнюю цитату. Ссылка ведёт
к окружению сообщения с его собственными правами, не превращает личную
переписку в знания команды. Структура контекста, календарные фильтры и
проверка источников описаны в [истории Ариса](agent.md#история-и-цитаты-сообщений).

## Идентификаторы и связи

`source_id` имеет вид `task:12` или `task_report:34` и разрешается внутри выбранного проекта. UUID точки детерминирован по проекту, источнику и номеру фрагмента. Payload содержит версию схемы, тип/ID, родителя, связи, текущие свойства, хэши текста/источника, модель/размерность embeddings и положение фрагмента.

Граф связывает задачи с документами, участниками, зависимостями, ИСР, стадиями, рисками, отчётами и вложенными источниками. Старые импортированные Markdown-копии сохраняют происхождение и пользовательские правки; новая загрузка создаёт только оригинал. Концы связей проверяются по текущему каталогу. `task_ids` обозначает связи, `owner_task_id` — принадлежность вложенного объекта; удаление задачи не должно удалять общий документ или риск.

## Синхронизация и восстановление

Оригинал сохраняется один раз у проекта либо задачи. Транзакция загрузки создаёт
задание независимой обработки `file_processing_jobs` и немедленный FTS-индекс
названия/подписи. Извлечение текста выполняется локальным парсером либо vision;
затем полный текст и поисковые фрагменты фиксируются одной транзакцией.
Изменение подписи обновляет поиск без повторного разбора оригинала или vision.

Далее работает прежний семантический путь: PostgreSQL outbox → снимок каталога
с уже сохранённым текстом → саммари → фрагменты → сверка Qdrant.
[Триггеры outbox](../backend/src/db/knowledge_outbox.py) создают не более одного
задания на пару «проект + транзакция», включая массовые SQL-операции и каскады.
Rollback откатывает и задание. После завершения извлечения ставится новое
проектное задание, поэтому ранняя индексация метаданных не теряет содержимое.
Изменения личных задач не ставятся в проектную семантическую очередь.

[KnowledgeQueueService](../backend/src/services/knowledge_queue.py) и [worker](../backend/src/knowledge/worker.py) объединяют задания проекта, восстанавливают прерванные попытки и повторяют ошибки до `KNOWLEDGE_INDEX_MAX_ATTEMPTS`. Новое изменение во время индексации остаётся отдельным заданием. Успешные задания очищаются по `KNOWLEDGE_JOB_RETENTION_DAYS`.

[KnowledgeIndexService](../backend/src/services/knowledge_index.py) использует один алгоритм для обычного изменения и ручного reindex. Неизменный текст переиспользует векторы; изменение свойств или связей обновляет payload. Новые текст, модель или размерность требуют embeddings. Лишние точки удаляются после записи актуальных. Qdrant не содержит уникальных бизнес-данных.

Снимок и результаты извлечения сохраняются в коротких DB-областях. Файловый разбор, vision, LLM-саммари, embeddings и Qdrant выполняются без удержания DB-соединения. Извлечённые оригиналы фиксируются до саммари; ошибка саммари не исключает исходный текст из поиска.

После восстановления PostgreSQL и `UPLOADS_PATH` следует применить `alembic upgrade head`, запустить backend/Qdrant и поставить `POST /api/v1/projects/{id}/knowledge/reindex`. Дождаться завершения очереди и проверить coverage, ошибки файлов и контрольное чтение источника. Пустая очередь сама по себе не доказывает полноту.

Перед обновлением существующей БД нужна проверенная резервная копия БД и uploads.
Миграции `a53c9e1f426b` и `b64da02f537c` добавляют схему поверх прежней цепочки,
без массового извлечения или backfill. После `alembic upgrade head` из `backend`
выполняется `python -m src.files.backfill --batch-size 200`: команда
пакетно и повторяемо заполняет FTS из метаданных и **уже сохранённого** текста,
без чтения оригиналов, vision, embeddings и изменения проектных векторов.
Флаг `--enqueue-missing` дополнительно ставит ранее необработанные оригиналы
в обычную очередь: их parser/vision будут вызваны работающим worker-ом.
Существующие задания, активные lease и успешные результаты не сбрасываются.

Миграция `e92a74c610bf` поверх `d86e1a90c427` добавляет общий контракт,
владение Markdown задачей, ссылки из комментариев и устойчивые квитанции.
Производный FTS-вектор Markdown пересоздаётся с подписью, исходные тексты
сохраняются. Для существующих источников ставится одна семантическая сверка
на проект без повторной постановки извлечения: готовый текст и векторы
переиспользуются, затем появляются фактические квитанции готовности.
Старые ссылки чата переводятся в `document_ref`; исторические результаты
действий получают производную ссылку без удаления исходного audit payload.
Незавершённые старые external API-ответы с неизвестными credentials помечаются
ошибкой с просьбой повторить вопрос после обновления авторизации; тексты вопросов,
авторы, завершённая история и cookie-диалоги сохраняются.
Откат останавливается, если старая схема не сможет сохранить новые
пользовательские данные. Перед обновлением существующей БД нужны backup БД и uploads.

## Документы: владение, каталог и обработка

В проекте и задаче используется одно понятие «Документы». Текстовый Markdown
можно создать, поддерживаемый оригинал — загрузить. Физические таблицы
`documents`, `project_files`, `task_attachments` сохраняются вместе с существующими
данными; единый [DocumentCatalogService](../backend/src/services/document_catalog.py)
обслуживает REST, MCP и Ариса. Новая загрузка не создаёт Markdown-дубликат.
Ранее импортированные и отредактированные документы не объединяются и не удаляются.

`document_ref` — стабильная непрозрачная ссылка с версией формата `d1_`.
Клиент получает её от сервера, не собирает из числового ID. Она сохраняется при
переносе задачи. При каждом чтении проверяются актуальный владелец, доступ
пользователя и scopes ключа; ссылка сама по себе прав не даёт.

Владение и связь различаются. Проектный документ может быть связан с несколькими
задачами того же проекта. Снятие связи сохраняет оригинал. Документ задачи следует
за своей задачей при переносе; связи со старым проектным контекстом снимаются
одной транзакцией. Личные документы не становятся знаниями общего проекта.

### Единый API

- `GET /api/v1/documents`: `project_id`, `task_id`, необязательный `q`,
  `scope=all|project|tasks`, `source_kind=text|upload`, `format`,
  `processing=all|pending|ready|failed`, `limit`, `offset`.
  Фильтры применяются до подсчёта и пагинации; документ показан один раз.
  `project` означает отсутствие владельца-задачи и любых связей с задачами;
  `tasks` включает владение и связи. Фильтры работают без поисковой строки.
- `POST /api/v1/documents`: JSON `request_id`, `title`, `content_md`,
  необязательный `caption`, ровно один из `project_id` / `owner_task_id`.
- `POST /api/v1/documents/upload`: multipart с тем же владельцем, `request_id`,
  `file`, необязательными `title` и `caption`. Ответ 201 возвращается до OCR/LLM.
- `GET`, `PATCH`, `DELETE /api/v1/documents/{document_ref}`: метаданные,
  изменение прочитанной `expected_revision`, удаление.
- `GET /{document_ref}/text?offset=0&max_chars=8000`: сохранённый Markdown либо
  извлечённый текст, хэш полного представления, Unicode-смещения и `next_offset`.
- `GET /{document_ref}/content`, `GET /{document_ref}/preview`: защищённый оригинал
  и локальная миниатюра; `POST /{document_ref}/retry`: повтор фоновой обработки.
- `POST` / `DELETE /{document_ref}/tasks/{task_id}`: создать / снять связь.

DTO содержит автора, владельца и связи, доступные действия, оригинал, текстовое
представление и отдельные стадии `extraction`, `fts`, `semantic`. Состояние
семантической индексации связано с точной версией содержимого: пустая очередь
или успешная индексация другого документа не означают готовность этого документа.
Повтор `request_id` с прежними аргументами не создаёт копию; с другими даёт 409.
Доступ повторно проверяется после ожидания блокировок и при воспроизведении квитанции.

Для ключа `telos_key_` чтение проектного документа требует `projects:read`,
документа задачи — `tasks:read`. Изменение требует `projects:write` либо
`tasks:write` по владельцу; право write не открывает чтение текста или оригинала.
Создание связи требует `projects:write` и `tasks:write`. Каталог фильтрует строки
по scopes до подсчёта и пагинации, `task_id` требует `tasks:read`.
Автор определяется сервером. Оригинал отдаётся с `private, no-store` и `nosniff`;
файловый ответ не удерживает DB-соединение во время скачивания.

### Извлечение и повторное использование текста

Оригиналы атомарно сохраняются локально под `UPLOADS_PATH`. Поддерживаются PDF
с текстовым слоем, DOCX, Markdown/TXT/CSV/LOG, Excel (`xls/xlsm/xlsx`) и изображения;
сканы PDF не получают OCR автоматически. Настроенная vision-модель распознаёт
изображения. Предел загрузки по умолчанию — 10 МиБ, подписи — 2000 символов.

Worker использует существующий путь `file_processing_jobs`: извлечение → сохранение
полного текста и FTS → outbox → саммари/embeddings/Qdrant. Markdown уже является
текстом. Кэш хранится в `knowledge_attachment_texts` / `knowledge_project_file_texts`;
изменение подписи, открытие, связь с задачей и чтение AI-контекста его переиспользуют.
Повтор сохраняет успешное извлечение. Ошибка embeddings не скрывает сохранённый
текст; отключённый semantic index не отключает извлечение и обычный поиск.

### Комментарии и представление

`POST /api/v1/tasks/{task_id}/comments/with-files` принимает multipart `request_id`,
`body_md`, повторяющиеся новые `files`, JSON `captions` и JSON `document_refs` для
существующих документов этой задачи. Нужны текст или документы; всего не более
десяти документов. Комментарий, новые оригиналы, связи, история, outbox и квитанция
фиксируются атомарно, незавершённые оригиналы компенсируются. DTO комментария
содержит `document_refs`; их карточки используют общий каталог. Требуются
`comments:write` и `tasks:write` при наличии документов, а для выбора проектного
документа — право его чтения. Удаление комментария сохраняет документы;
удаление оригинала или снятие проектной связи убирает соответствующую ссылку.

[DocumentList](../frontend/src/components/documents/DocumentList.tsx) и
[DocumentView](../frontend/src/components/documents/DocumentView.tsx) используются
в проекте, задаче, комментариях и правой панели чата. Одна карточка показывает
оригинал, текст, автора, подпись, связи и стадии обработки. Созданный Markdown
редактируется с проверкой версии. Длинный текст читается страницами, ошибки и
неготовые состояния отображаются явно. Миниатюры изображений строятся локально,
не зависят от OCR и не заменяют оригинал. Закрытие диалога возвращает фокус.

## Поиск и чтение

Обычный поиск файлов использует `file_search_chunks.search_vector`: сохраняемый
взвешенный `tsvector` с GIN-индексом, название, подпись и полный извлечённый текст.
Текст разбивается на ограниченные перекрывающиеся окна, чтобы хвост большого
файла сохранялся в индексе и не превышался предел PostgreSQL на размер вектора.
Markdown-документы используют существующий `documents.search_vector` с GIN.
Результат содержит лучшее совпадение на источник, релевантность, фрагмент с
безопасными маркерами подсветки, источник и задачу, общее число и страницу.

Пользовательский поиск выполняется через единый `GET /api/v1/documents?q=...`
с теми же фильтрами владельца, задачи, формата и обработки, что обычный каталог.

При `KNOWLEDGE_ENABLED=false` или недоступных embeddings/Qdrant остаются
PostgreSQL-чтение, обработка файлов и FTS; агентская очередь продолжает работать.

[KnowledgeSearchService](../backend/src/services/knowledge_search.py) получает семантических кандидатов; [ProjectQueryService](../backend/src/services/project_query.py) объединяет их с FTS через RRF и читает текущие свойства из PostgreSQL. Чужие, удалённые и устаревшие фрагменты не становятся фактами ответа. Фильтр `entity_type` поддерживается обоими путями. `matched_locations` помогает дочитать найденный участок оригинала.

Общий контракт [KnowledgeReadRequest](../backend/src/schemas/knowledge.py):

- `telos_list_sources` — перечень; `telos_search_sources` — полнотекстовый поиск по каталогу;
- `telos_read_source` — текст источника; `telos_list_related_sources` — переходы по графу;
- `offset` / `next_offset` — продолжение страницы, `entity_type` — фильтр;
- по умолчанию пять объектов (максимум 30), текст 4000 символов (максимум 8000).

В MCP это `telos_read_project_knowledge(project_key, request)`. Семантический retrieval доступен через `telos_search_project_knowledge`; публичные адаптеры проверяют доступ и `knowledge:read` для ключей. SQL-чтение источника не требует вызова LLM. Агент принимает ссылки только на проверенные источники текущего запроса; текст документа или вложения не является системной инструкцией.

### Проверяемые фрагменты Ариса

Источник документа содержит `document_ref` и, при наличии точного совпадения,
`reference`: представление `markdown` / `extracted_text`, SHA-256 полного текста,
`start`, `end`, `quote`, `offset_unit=unicode_codepoints`. Диапазон и цитату
формирует сервер из разрешённого текста. Модель выбирает выданный `fragment_handle`;
произвольные координаты или цитата модели не становятся доверенной подсветкой.
Основной источник отмечается сервером, остальные доступны для переключения и закрепления.

Карточка открывает общий просмотр документа, загружает страницу нужного диапазона,
прокручивает и выделяет его. При изменении хэша показывает, что документ изменён,
и не переносит старое выделение на новый текст. Для изображений выделяется сохранённый
распознанный текст; координаты на картинке не выдумываются. Саммари источника само
по себе не является доказательством точной цитаты.

## Паспорт проекта — TELOS-25

Паспорт расширяет существующий `description_sections`: `problem`, `goal`,
`expected_result`, `additional`, `audience`, `capabilities`, `boundaries`,
`constraints`, `glossary`, `decisions`, `open_questions`. Все поля необязательны;
пустое поле означает неизвестное. Состав команды читается из команды проекта,
а не копируется в поле аудитории. Свободный прежний Markdown сохраняется полностью;
из его заголовков автоматически не извлекаются утверждённые цель и ограничения.
Ссылки на подтверждающие материалы человек может указать в нужном разделе.

HTTP-проект возвращает текущие полные разделы и `context_revision`. Компактный
`context` содержит ревизию, превью только заполненных полей до 160 Unicode-символов,
`unknown_fields` и `truncated_fields`. Это данные о заполнении, а не оценка
достаточности или достоверности проекта. Арис получает компактное представление
в начальном контексте и через `telos_get_project` / `telos_update_project`;
полный паспорт дочитывает существующим `telos_read_source` по `project:<id>`.
MCP `telos_get_project` сохраняет прежнее чтение `full_text=true` и дополнительно
возвращает ревизию/компактный контекст. Такое чтение не вызывает LLM и embeddings.

Изменение паспорта и настроек доступно владельцу проекта; это одинаковое правило
HTTP, доменного сервиса и существующего действия Ариса. Члены проекта читают
текущий паспорт и историю с обычными scopes. Сервер проверяет актуального владельца
после блокировки строки. `PATCH /api/v1/projects/{id}` принимает необязательный
`expected_context_revision`; при переданной устаревшей версии возвращает 409 без
записи. UI всегда передаёт прочитанную ревизию для правки разделов, Арис получает
такую инструкцию в схеме действия. Пропуск версии внешним клиентом сохраняет
обычную семантику PATCH; сервер всё равно назначает собственную новую ревизию.
Вложенный `description_sections` также имеет PATCH-семантику: неприсланные
разделы и их исходные строки сохраняются, явная пустая строка очищает только
свой раздел. Слияние выполняется под блокировкой строки; прежний свободный текст
сохраняется в additional, если это поле явно не изменяли.

Форма отправляет изменённые поля. При конфликте черновик остаётся открытым;
пользователь выбирает актуальную версию либо перенос своих правок поверх неё.
Нетронутые разделы/метаданные берутся из свежего проекта. Смена проекта создаёт
отдельное состояние формы и не переносит в него старый черновик или поздний ответ.

Содержательная правка увеличивает `context_revision` и атомарно сохраняет полный
снимок в `project_context_history`; no-op, смена названия/цвета/статуса и даты
сами по себе версию паспорта не увеличивают. Новый проект начинает с версии 1
и известного серверу автора. Для прежнего проекта до первой правки остаётся 0;
при первой правке сохраняется baseline 0 с неизвестным историческим автором,
а дата baseline означает момент его фиксации. Автор новых правок определяется
по локальному пользователю, а не по телу запроса. Откат транзакции откатывает
также историю и outbox.

`GET /api/v1/projects/{id}/context-history?limit=20&offset=0` возвращает страницу
метаданных: ревизию, автора, время, начальный снимок, изменённые поля и курсор
следующей страницы. Лимит — до 50. Полные исторические тексты в эту выдачу не
включаются и не дублируются в общем индексе. История видна в настройках проекта.
Миграция `f23a8c91d046` поверх `f23d8b410ce2` добавляет только схему без backfill;
downgrade с сохранённой историей запрещён. Установщик outbox сверяет поля с
фактической схемой, чтобы старые миграции не создавали триггер на будущую колонку.
Проверка downgrade сериализована с авторами правок блокировками projects → history
до проверки наличия снимков; запись между проверкой и удалением таблицы исключена.

### Первичные сведения и производная карта

Паспорт — утверждённое человеком описание проекта. Сохраняются существующие
разделы и Markdown; дополнительные поля необязательны. Пустое поле означает
«неизвестно», а не отсутствие проекта, отсутствие работы или завершение проекта.
Цель, результат, аудитория, текущие возможности, границы, ограничения, термины,
решения и открытые вопросы заполняются из доступных сведений. Автоматическое
предложение имеет происхождение и становится авторской правкой после явного
поручения/принятия через обычный WriteGate. Производная карта не перезаписывает
цель и ограничения. Данные в документах и репозиториях не дают разрешения на запись.

Минимальная единица карты — утверждение, связанное с одной или несколькими
версиями источников. Для него обязательны:

- стабильный ID, `project_id`, текст и вид: требование человека, факт источника,
  аналитический вывод, предположение или открытый вопрос;
- происхождение и автор: человек, опубликованный отчёт, код, CI, выкладка либо
  внешний материал; вывод LLM сохраняет модель/версию алгоритма и входной набор;
- ссылки на точные версии/фрагменты, время проверки и полнота рассмотренных материалов;
- состояние: актуально, устарело, заменено, противоречиво или недоступно;
  причина перехода и история замены;
- отдельное состояние принятия предложения человеком. Свежий вывод LLM сам
  по себе не становится утверждённым требованием или независимым доказательством.

Текущая карта использует `grounded_literal_v1`: паспорт имеет происхождение
авторского описания, документ — непроверенного источника, отчёт — сообщения
участника о результате. Состояние «задача завершена» без отчёта даёт только
сведения о статусе и явный пробел доказательств. Цели, причинные объяснения
и независимое подтверждение результата алгоритм не выдумывает. Неизменённые
разобранные версии переиспользуются; первоначальный SQL-снимок каталога всё ещё
читается целиком и учитывается отдельно в `catalog_chars_read`.

Исторические публикации отчётов сохраняются, а текущие утверждения используют
последнюю публикацию. Пропуск прежней версии с `task_report_not_current` пока
учитывается в общем охвате как ограничение: карта может оставаться `partial`
даже после разбора актуального отчёта. Это консервативная диагностика каталога;
удалять историю ради состояния `ready` нельзя.

На вкладке «Знания» доступны утверждения по разделам, происхождение, версии,
цитаты, пробелы, охват, поиск по актуальному тексту и чтение карты кода.
В «Обзоре» видны статус обработки и переход к карте. `/knowledge/map`,
`/knowledge/map/status` и `/knowledge/map/claims/{id}`
только читают сохранённое состояние; `/knowledge/map/refresh` ставит работу в
очередь и доступен владельцу. Чтение карты само не обращается к Git или LLM.

Версия источника включает ID источника, проект, собственную ревизию либо
неизменяемый внешний идентификатор, хэш содержимого, время наблюдения и
версию представления. Фрагмент привязан к этой версии и точным Unicode-смещениям
либо строкам кода; цитата сверяется с текстом. Если оригинал исторической версии
не сохранён, ссылка сообщает недоступность этой версии и не открывает новый
текст под старой цитатой. Удаление/отзыв доступа сохраняют допустимый аудит,
но закрывают содержимое и производный пересказ для утратившего доступ читателя.

Опубликованный отчёт подтверждает, что участник сообщил результат. Сам факт
закрытия задачи подтверждает только смену состояния. Для разработки доказательства
хранятся независимо: предложение PR, код выбранного ref, проверка конкретного SHA,
выкладка конкретной версии компонента в конкретной среде. Эти признаки не образуют
необратимую шкалу: переоткрытие, failed CI и rollback пересматривают текущий вывод.

### Доступ и ответственность каналов

Источник, его версия и все доказательства утверждения проверяются по текущему
доступу пользователя. Общие знания проекта не включают приватные диалоги, память,
draft и файлы чата без явной публикации в проект. Личные материалы остаются в
личном контуре. `global` выбирает доступный проект явно; контекст страницы,
UUID, путь, ID подключения и handle не расширяют права.

HTTP, MCP и Арис используют один доменный сервис. Адаптеры проверяют principal
и scopes; сервис проверяет принадлежность/членство и версию при операции.
`DocumentCatalogService` сохраняет существующие права по владельцу документа;
новые инструменты карты, отбора, Git и веб требуют одновременно `knowledge:read`
и `projects:read`. `agent:ask` сам по себе их не открывает. Управление проектом
требует `projects:write`; связи Git с задачей дополнительно требуют `tasks:read`
либо `tasks:write` по операции.
Владелец проекта управляет Git-подключениями. Токен GitHub добавляется,
заменяется и удаляется в разделе GitHub собственного профиля.

Подключение закрытого репозитория — явное предоставление разрешённого содержимого
команде данного проекта. В форме подключения видны область и круг читателей;
локальные права проверяются отдельно. Все запросы к GitHub, включая чтение
публичных репозиториев и фоновые проверки, используют токен владельца из профиля.
Достаточен токен с чтением выбранных репозиториев. Секрет хранится на сервере
в зашифрованном виде, а worker использует ID и ревизию привязки. При замене или
удалении токена доступ закрывается до успешной проверки. Репозитории, связи и
позиция индексации того же SHA сохраняются. После миграции существующие
подключения возобновятся, когда владелец добавит токен в профиль. После передачи
проекта новый владелец может привязать свой уже настроенный токен через
«Проверить обновления».
Перед выдачей закрытого текста и публикацией ответа проверяется актуальная
доступность внешнего источника. Невозможность подтвердить внешний доступ закрывает
чтение его сохранённого корпуса до успешной проверки; остальные источники работают.
Для Git проверяется чтение разрешённого Git-объекта с `Contents:read`:
одних метаданных репозитория недостаточно. Публичность upstream-репозитория
не открывает проектные snapshots, аннотации и связи посторонним участникам.

Все источники, которые прочитала модель, входят в серверный набор проверок
публикации, даже если она не вернула handles. Непосредственно перед ответом
повторно проверяются ACL, версии, хэши и выбранные фрагменты. Изменение значимого
входа прерывает публикацию устаревшего ответа; переименование карточки не обновляет
доказательство. Сохранённые карточки также проверяются при последующем чтении.

UI показывает паспорт, предложения, происхождение, обновление, ошибки и пробелы
в существующей оболочке. Оно не решает права и не объявляет пустую очередь
доказательством полноты. Новые операции регистрируются единожды под каноническими
именами `telos_<действие>_<сущность>`; HTTP/MCP/Арис не получают отдельных обходов.
Запись сохраняет WriteGate, подтверждение опасных действий и квитанции повторов.

### Несколько репозиториев и внешнее исследование

Проект имеет 0…N независимых подключений; один репозиторий может содержать несколько
компонентов, а задача — изменения в нескольких репозиториях. У подключения есть
локальный ID, provider, числовой ID репозитория у провайдера, имя/назначение,
выбранный ref, разрешённая область, ID/ревизия credential-привязки и состояние.
Owner/name — координаты, а не единственная идентичность репозитория.

Ref сначала разрешается в commit SHA. Источник кода адресуется набором
`project + connection + repository + commit SHA + POSIX path + blob SHA`;
диапазон/хэш представления дополняют фрагмент. Одинаковые пути/символы разных
репозиториев не объединяются. Первый провайдер — GitHub; клиент выполняет только
чтение метаданных, commit/tree/blob и сравнение SHA. Ссылки `download_url`,
symlink, submodule и код репозитория не исполняются и не обходятся автоматически.
Секреты, `.env`, credentials, бинарные/генерируемые файлы и зависимости исключаются
политикой сканирования до передачи LLM/индексатору.

Для каждого подключения отдельно сохраняются `observed SHA/at`,
`indexed SHA/at`, поколение выбранного ref, охват и причина неполноты/ошибки.
Общий manifest содержит набор версий; независимые сканирования не называются
атомарным снимком проекта. При сохранённом доступе прежний завершённый snapshot
можно читать с явной отметкой устаревания. Частичный обход дерева не разрешает
удалять неувиденные файлы предыдущего snapshot. Лимиты и `truncated` провайдера,
включая ограниченный список файлов compare, означают неполноту, а не отсутствие
изменений ([GitHub trees](https://docs.github.com/en/rest/git/trees#get-a-tree),
[compare](https://docs.github.com/en/rest/commits/commits#compare-two-commits)).

Связи задача↔PR/commit имеют кратность N:N и repository ID. CI относится к точному
SHA; выкладка — к компоненту, SHA и среде. Успешная проверка/выкладка одной части
не подтверждает другие; неизменный третий репозиторий не обязан участвовать в задаче.
Отключение одного источника не удаляет проект, задачи и другие подключения.

Внешний поиск получает только отдельно сформированную публичную тему после
серверного разрешения. Проектные документы, приватная переписка, код, credentials
и персональные данные в поисковый запрос не передаются. Клиентский флаг разрешения
не является аргументом инструмента модели. Первый адаптер — Brave Web Search;
его ключ и включение задаются отдельно, без подмены LLM/embedding-настроек проекта.
Результат содержит URL, время получения, доступную дату/версию, хэш прочитанного
текста и охват; поисковый snippet не означает прочитанную страницу.
Чтение ограничено внешними HTTP(S), проверенными DNS/IP и редиректами без доступа
к внутренним адресам. Источник считается данными. Сохранение исследования в проект
выполняется отдельным разрешённым действием с происхождением.

Арис сначала предлагает `telos_request_web_search(public_topic)` либо
`telos_request_web_page(url)`. Человек видит точную тему/URL и разрешает внешний
запрос отдельно. Только сервер выпускает подписанный grant, связанный с
пользователем, проектом, назначением и сроком до 15 минут. READ-токен может
подтвердить такой внешний read effect; это не разрешает запись в проект.
Модель передаёт grant в `telos_search_web`/`telos_read_web_page` и не может
заменить тему произвольным текстом. `telos_save_web_research` отдельно проверяет
текущий хэш страницы и сохраняет документ через обычный WriteGate/UUID-квитанцию.
Повтор сохранения проверяет прежнюю квитанцию до нового сетевого обращения.

При создании проекта и в его настройках можно выбрать несколько репозиториев
из каталога GitHub с поиском или добавить сторонний репозиторий по ссылке.
Подключения обрабатываются независимо. При лимите отображаются сохранённый
прогресс и время следующей попытки. Карта кода находится в настройках проекта,
Git-доказательства — во вкладке отчёта задачи. Найденные по ключу задачи PR/commits остаются
предложениями до явного связывания. Python-разбор использует AST; JS/TS-разбор
лексический, поэтому его кандидаты и неполнота явно отмечены. Текущая выкладка
подтверждается только однозначным активным успешным состоянием по точному SHA
и среде; время события, зелёный CI и merge сами по себе этого не доказывают.

### События, публикация и восстановление

В одной бизнес-транзакции сохраняются изменение первичных данных и outbox.
Исходные документы/файлы, общий каталог и существующий механизм очереди сохраняются;
новый параллельный knowledge-контур не создаётся. Производные таблицы не ставят
сами себя в бесконечную переиндексацию. Единицы обработки разделяются по источнику
и поколению версии; проектное объединение заданий не теряет изменения разных repo.

| Событие | Что пересматривается |
|---|---|
| Правка паспорта, документа, опубликованного отчёта | Зависимые утверждения/фрагменты по версиям источников; принятый паспорт меняет только его авторская операция |
| Завершение/переоткрытие задачи | Происхождение результата и его актуальность, без выдуманного исполнения или автоматического подтверждения продакшена |
| Push/PR/merge | Соответствующее подключение/ref; предложение и основной код учитываются раздельно |
| CI/deploy/rollback | Точное доказательство SHA/компонента/среды, независимо от стадии задачи |
| Удаление, перенос, отключение, отзыв доступа | Немедленное закрытие выдачи по актуальному ACL, затем очистка/инвалидация индекса и зависимых выводов |

Webhook проходит проверку подписи и repository binding, delivery ID дедуплицируется.
Порядок доставки и Git timestamps не задают порядок версий. Worker проверяет
поколение подключения и актуальный целевой SHA, поддерживает force-push и rollback;
пропущенные события обнаруживаются ограниченной сверкой ref. Для продакшен-webhook
предусмотрен HTTPS-приёмник ([рекомендации GitHub](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)).

Внешние вызовы идут вне DB-соединения. Публикация карты выполняется короткой
транзакцией с проверкой входного manifest/generation и текущих прав. Запоздавшая
работа не заменяет новую карту; смена A→B→A различается поколением, а не только хэшем.
Повтор использует checkpoint и результаты неизменного содержимого; ошибочная
попытка остаётся видимой. Новый снимок становится текущим после проверки полноты
своего заявленного охвата. Сбой одной части оставляет другие доступными и явно
ограничивает общую картину. Qdrant восстанавливается из первичных/производных
сохранённых версий, а не служит единственной копией утверждений.

### Минимальная схема и порядок миграций

В локальных исходниках добавлена одна последовательная цепочка:
`f12c7a309bd1 → f23d8b410ce2 → f23a8c91d046 → c26a202611160001 → c29a202611160001`.
Она проверяется на изолированном PostgreSQL; работающая БД этим не обновляется.

| Этап | Изменение PostgreSQL |
|---|---|
| TELOS-25 | Расширить существующий `description_sections`; добавить ревизию паспорта и историю снимков с автором/временем. Исходный Markdown не анализируется с выдуманным заполнением полей |
| TELOS-26 | Версии источников/manifest, утверждения, их evidence-связи и история замены. Первичные документы остаются в текущих таблицах; кэш саммари не становится реестром фактов |
| TELOS-29/30 | Подключения/credential-привязки, версии и файлы Git-источников с локальными ID, checkpoint и независимым состоянием индекса каждого repo |
| TELOS-31/32 | Квитанции событий, поколения целевого ref, N:N-связи задач с изменениями и доказательства CI/deploy по SHA/среде |
| TELOS-33 | При явном сохранении — существующий документ с происхождением веб-материала; временный поиск не создаёт скрытый источник проекта |

Миграции продолжают текущую единственную цепочку Alembic и регистрируют политику
новых таблиц в каталоге. Перед обновлением действующей БД проверяются резервные
копии БД/uploads. DDL не запускает массовые LLM/извлечение/backfill. Существующим
описаниям не приписываются авторы и даты прошлых правок: первая известная версия
помечается как исходное состояние. Downgrade останавливается, если новые данные
невозможно сохранить. Фоновые backfill выполняются отдельно, порциями и повторяемо.

### Бюджеты и приёмка этапов

Исходные лимиты в [AgentSettings](../backend/src/core/settings.py) и
[runtime](../backend/src/agent/runtime.py): 12 000 локально оценённых токенов
контекста, 1 200 истории, 15 сообщений, 8 предметных шагов, до 8 инструментов
за шаг и 4 000 output tokens ответа. С deferred loader это до 12 model requests
и 80 tool calls с учётом резервов; без loader — до 10/64. Deadline хода — 600 с,
синхронное ожидание ask — 25 с, затем polling. Локальная оценка контекста не равна
фактическим оплачиваемым токенам провайдера. Новые инструменты укладываются в эти
пределы, а не увеличивают их скрыто.

Для новых адаптеров установлены целевые пределы: Git JSON ≤8 МиБ,
blob ≤1 МиБ, до 10 000 entries дерева за результат с явным охватом; запрос ≤10 с,
до двух попыток только для допускаемых транспортных/5xx ошибок. Rate limit
возвращается очереди без немедленного повтора. Веб-чтение/поиск — общий deadline
20 с без retries, ответ ≤1 МиБ, извлечённый текст ≤20 000 символов и до трёх
проверенных редиректов. Таймаут включает DNS и чтение; размер ограничивается до
неограниченной загрузки/распаковки. Больший материал имеет явную неполноту либо
ошибку лимита, а не успешный пустой результат.

Git foreground имеет общий предел 32 фактических HTTP attempts на ход, включая
retries и проверки источников; фоновая lease — до 4 attempts. Snapshot ограничен
10 000 путей и 20 МиБ текстов, blob — 1 МиБ. Worker читает порции по
`GIT_SYNC_BATCH_FILES` (по умолчанию 20), сохраняет checkpoint и продолжает
отдельное поколение каждого подключения. Исчерпание бюджета означает partial
либо отказ проверки, без объявления источника удалённым или проверенным.

Фоновое построение карты использует до 32 000 символов одного исходного
фрагмента, 128 000 символов, 64 источников и 512 утверждений за порцию;
deadline — 300 с. Длинные источники продолжаются с checkpoint и видимым охватом.
Текущий алгоритм не вызывает модель: `model_requests=0`, стоимость остаётся
`null` с пояснением `no_model_requests`. Возможный будущий LLM-разбор ограничен
4 HTTP attempts и 2 000 output tokens на запрос; это предел, а не измерение
нынешнего алгоритма. Повторная платная отправка должна учитываться в usage.

Чтение сохранённого паспорта/карты/страницы не вызывает LLM, vision и embeddings.
Семантический поиск отдельно учитывает query embedding. Измеряются фактические
model requests, input/output tokens, cache reuse, retries, длительность стадий,
объём прочитанного/пропущенного, возраст версии и причины неполноты. Стоимость
берётся из фактического provider cost при наличии, иначе вычисляется по usage
и датированному тарифу модели. Без этих сведений, в том числе для оплаченного
неуспешного запроса, она остаётся неизвестной, а не нулевой. Baseline, p95
и денежные пределы не выдумываются из timeout.

| Этапы | Обязательные проверяемые сценарии |
|---|---|
| 02 | Пустой и заполненный паспорт при нуле задач; сохранение исходного описания, частичное заполнение, конфликт правок, история автора и длинное чтение |
| 03–04 | Смена версии, противоречие текущих источников, удаление и revoke между чтением/ответом; неполный поиск отличается от отсутствия данных; shared/private-project/global и draft изолированы |
| 05 | Ясное поручение, существенный пробел, обсуждение, большая идея, дубль; качественный черновик и реальная карточка после разрешённой записи, без вымышленных сроков/людей |
| 06 | Закрытие с отчётом/без отчёта, исправление результата и переоткрытие; никакого ложного подтверждения исполнения/выкладки |
| 07–08 | 0/1/3 repo, разные ref/SHA, одинаковые path/symbol, большой/исключённый файл, неполное дерево, недоступность одного подключения и forged ID; цитаты сохраняют идентичность каждой части |
| 09–10 | Дубли/перестановка событий, одновременные push, crash/restart, slow old job, force-push/rollback; одна задача с PR в двух repo, CI на другом SHA, staging и prod с разными версиями |
| 11 | Только одобренная публичная тема, пустой/частичный поиск, устаревшая страница, redirect/DNS→internal и prompt injection; сохранение исследования отдельным действием |
| 12 | Сквозной цикл с/без Git во всех чатах; исходные данные сохранены, понятные пробелы/свежесть, измеренные вопросы/ошибочные действия/время/usage |

Синтетические входы и ожидания поддерживаются в тестовых fixtures; проверка их
согласованности не является проверкой продукта. Неисполненные сценарии остаются
`not_run`. Транспортные/модельные дублёры проверяют алгоритмы и ошибки, настоящий
PostgreSQL — транзакции/гонки/миграции, живой провайдер — фактическую интеграцию,
настоящая модель — качество формулировки и выбора контекста. Результаты и ограничения
каждого этапа фиксируются в соответствующей задаче. Окончательная приёмка TELOS-34
дополняет, а не заменяет проверки предыдущих этапов.

Сквозные проверки используют те же общие сервисы и этот контракт. Наличие
адаптера и корректной fixture само по себе не завершает соответствующую задачу.

## Настройки, диагностика и развитие

Веб: `WEB_RESEARCH_ENABLED`, `BRAVE_SEARCH_API_KEY`, `WEB_RESEARCH_GRANT_TTL_SECONDS`.
Без ключа Brave поиск показывает недоступность; прямое разрешённое чтение
публичного URL работает независимо. Ключ не заменяет настройки модели/embeddings.
Git: `GIT_CREDENTIALS_KEY` — отдельный Fernet-ключ сервера для шифрования credentials,
`GIT_POLL_INTERVAL_SECONDS` (60) и `GIT_SYNC_BATCH_FILES` (20).
Fernet-ключ обязателен для сохранения токена GitHub в профиле.
Ключ шифрования нужно сохранять отдельно вместе с защищённой конфигурацией:
его потеря делает сохранённые credentials нечитаемыми. В БД/DTO/модели секреты
не расшифровываются для отображения. События GitHub используют отдельную HMAC
подпись и delivery ID; пользовательский API-ключ её не заменяет.

Параметры — в [backend/.env.example](../backend/.env.example) и [settings.py](../backend/src/core/settings.py): `KNOWLEDGE_ENABLED`, `QDRANT_*`, `EMBEDDING_*`, `KNOWLEDGE_CHUNK_TARGET_CHARS`, `KNOWLEDGE_CHUNK_OVERLAP_CHARS`, `KNOWLEDGE_INDEX_*`, `KNOWLEDGE_VISION_ENABLED`, `KNOWLEDGE_SUMMARY_CHUNK_CHARS`. Независимая обработка файлов использует `FILE_PROCESSING_POLL_SECONDS`, `FILE_PROCESSING_MAX_ATTEMPTS`, `FILE_PROCESSING_LEASE_SECONDS`, `FILE_PROCESSING_RETRY_SECONDS`; задания захватываются с `SKIP LOCKED`, lease продлевается вне внешних вызовов. Изменение модели или размерности embeddings требует согласованной пересборки производного индекса.

`GET /api/v1/projects/{id}/knowledge/status` показывает `enabled`, `ready`, очереди, последнюю ошибку, `coverage` по типам (`total/indexed/missing/stale`), лишние точки и `file_issues`. Наличие коллекции или `points_count > 0` не равнозначно готовности. Статус, диагностика и ручной reindex доступны рядом с проектным агентом.

Новый источник требует политики каталога, правильной проектной принадлежности, триггера outbox, FTS/чтения/связей и проверки эквивалентности обычной индексации и reindex. Тесты с подменёнными embeddings/LLM подтверждают контракты, но не качество ответов живой модели.
