# Общий чат проекта

Вкладка **Чат** находится внутри проекта второй, сразу после **Обзора**: `/projects/:projectKey/chat`. Это одна общая история для команды. Обращение «Арис, …» или «ARIS, …» вызывает Ариса, проектного менеджера TELOS SPACE; его ответ видят участники чата. Личная переписка с Арисом хранится отдельно от общей и видна только владельцу.

Во вкладке проекта нет выбора переписки и дополнительных меню личного чата.
Отдельной проектной вкладки «Агент» нет. Меню «Проектные диалоги и знания» на
странице `/chat` открывает приватные проектные диалоги на
`/projects/:projectKey/conversations` или диагностику/переиндексацию знаний
на `/projects/:projectKey/knowledge`. Это самостоятельные страницы;
просмотр знаний не загружает приватную историю диалогов.

Текущее состояние и результаты проверок — в [памяти проекта](../MEMORY.md), runtime и подтверждения Ариса — в [agent.md](agent.md).

## Чаты поверх любого экрана

Одна компактная кнопка **Чаты** открывает общее окно. Выбор в его шапке:
«Личный — Арис» или доступный проект с ключом и названием. Под переключателем
видно, кому доступны сообщения. Постоянного выбора проекта поверх дашборда нет.
Внутри проекта первое открытие показывает его общий чат; вне проекта — последний
выбор пользователя, а при первом запуске личный диалог. Открытая переписка
закреплена за выбранным чатом и не меняется при навигации по страницам.

На `/projects/:projectKey/chat` и `/chat` скрыты плавающее окно и его кнопка.
Проектная вкладка показывает только общий чат текущего проекта. Выбор переписки
доступен в общем окне и на странице `/chat`. Общий чат разворачивается в проектную
вкладку, личный — всегда в `/chat`. Личный чат использует историю
`/api/v1/aris/conversations` и сохранённый выбор диалога. Приватные проектные
диалоги и знания доступны из меню на `/chat` и по прямым ссылкам; кнопка «Общий чат»
возвращает из них в переписку проекта.
Истории и черновики личного и общего режима раздельны; переход между окном
и страницей сохраняет переписку, вложения и черновики, включая редактирование.
Поиск в окне не меняет URL основного экрана. Разворачивание сохраняет параметры
открытой задачи, подтверждения и hash; ссылка на сообщение другого проекта снимается.
На телефоне окно полноэкранное, его закрытие и выбор чата остаются доступны.

Полный проектный чат делит рабочую область на переписку и контекст. От 1280 px
справа открыта панель шириной 360–460 px; история и редактор слева ограничены
900 px и смещены чуть левее центра; у панели есть внешний отступ 12 px по
вертикали и 16–24 px справа, фирменная рамка и акцент заголовка.
Панель можно закрыть и вернуть кнопкой «Контекст». На меньшем экране
контекст открывается по кнопке или карточке отдельным адаптивным листом.
Основной текст сообщений и редактора — 14 px, подписи вкладок — 15 px.
На узком экране вкладки прокручиваются отдельно, активная вкладка остаётся видимой.

Карточка задачи из сообщения или ответа Ариса открывает общий `TaskDialog`,
как в списке задач или канбане, и сохраняет выбранную задачу в контексте справа.
После закрытия остаются выбранный объект и черновик сообщения. На телефоне
открывается только модальная карточка задачи; контекст доступен отдельно по кнопке.
Карточки всех документов открывают общий `DocumentView` рядом с перепиской:
оригинал, сохранённый текст, сведения и действия доступны в одной карточке. Пункты списка объектов в правой панели выбирают
предпросмотр без открытия модального окна.
Внизу панели — последние объекты из загруженной переписки. После завершённого ответа Ариса контекст выбирает подтверждённый основной
источник, даже если в ответе несколько документов; проверенная цитата
прокручивается и выделяется по точному хэшу и Unicode-диапазону. Изменённый
документ показывается с предупреждением и без устаревшей подсветки;
закрепление удерживает выбор, ручное переключение остаётся доступным.
Новый ответ не открывает закрытую панель, мобильный лист или модальное окно задачи.

Карточки сущностей Ариса во всех чатах и результатах действий используют
единый голубо-фиолетовый акцент. Выбранная карточка и клавиатурный фокус
различимы; семантические цвета статусов и приоритетов остаются прежними.

Контекст использует только идентификаторы серверных карточек и существующие
защищённые API. Недоступный или перенесённый в другой проект объект не раскрывает
прежнее содержимое. Дополнительных запросов к модели, истории или WebSocket
панель не создаёт. В компактном окне карточки сохраняют обычные переходы.

`ChatWorkspace` находится над маршрутизацией приложения и выбирает проект для единственного `ProjectChatProvider`. Переходы между вкладками, окном и общими экранами не создают дополнительный WebSocket. `ProjectChatWorkspace` переиспользуется в обоих представлениях. Смена проекта окна не перемонтирует основной экран. Чтение отмечается только для видимых сообщений; свёрнутое окно не отмечает новые сообщения прочитанными.

## Возможности

- История в PostgreSQL, последние 50 сообщений при открытии, загрузка ранних страниц с сохранением позиции прокрутки.
- На touch-экране Enter добавляет строку; отправка выполняется кнопкой или Ctrl/Cmd+Enter.
  На компьютере сохранены Enter для отправки и Shift+Enter для новой строки.
  Редактор растёт до доступной высоты; вход в чат не вызывает клавиатуру автоматически.
  Чтение ранних сообщений не прерывается автопрокруткой; перейти вниз можно явной кнопкой.
- Отправка по WebSocket, состояния отправки и безопасный повтор с тем же UUID. Черновик переживает перезагрузку вкладки.
- Ответ на сообщение, цитирование выделенного фрагмента, ограниченный Markdown без HTML.
- Структурированные упоминания участников через `@`, реакции `👍 ❤️ 👀 ✅ 🎉`.
- Правка своих сообщений с контролем версии, мягкое удаление и отметка в ответах на удалённое сообщение.
- Защищённые вложения, предпросмотр растровых изображений, скачивание остальных файлов.
- Поиск по сообщениям с русской морфологией и переходом к окружению результата.
- Личная граница прочтения, разделитель, счётчик во вкладке, уведомления о сообщениях вне активного чата.
- Online/typing с TTL; несколько вкладок одного участника учитываются независимо.
- Карточки задач, документов, рисков, вех и разделов ИСР. `#` открывает поиск объектов проекта. Ссылки открывают соответствующую панель или экран.
- Ответы Ариса имеют отдельный тип автора и подпись в истории, поиске, цитатах и уведомлениях. Событие `task.moved` обновляет карточки и зависимый кэш; уведомления изолированы по текущим проекту и пользователю.

## Арис в командном чате

Обращение сохраняет задание в `chat_agent_turns`. Общий AgentWorker выполняет
его через ArisChatService и тот же runtime/каталог действий, что у проектного
интерфейса. Доступ инициатора и актуальная попытка повторно проверяются перед
чтением, записью и публикацией ответа. Режим `project_chat` не открывает личные
задачи, доски и другие проекты инициатора.

WriteGate не заменяет подтверждения опасного действия. Работа очереди,
идемпотентность и права описаны в [agent.md](agent.md); доменные изменения
проходят через общие сервисы. Личная память пользователя не публикуется в чате.

## Lifecycle и доступ

Миграция `f29c7618a403` создаёт восемь таблиц и триггеры. PostgreSQL автоматически создаёт `project_chats` в транзакции добавления нового проекта; уникальность `project_id` исключает второй чат. **Backfill существующих проектов отсутствует** по принятому решению. Для такого проекта вкладка показывает, что чат недоступен.

Отдельной таблицы участников чата нет: источник прав — `project_members` и активность пользователя. Новый участник видит всю историю, а его начальная граница прочтения устанавливается на последнее сообщение. Удаление участника или отключение пользователя создаёт событие отзыва доступа; получив его через Redis, каждый экземпляр закрывает все сокеты этого участника с кодом `4403`. Каждая постоянная операция и heartbeat повторно проверяют права в БД.

HTTP и WebSocket используют cookie или прежние `telos_token_`-токены. READ-токен читает историю, файлы и карточки; изменение сообщений, реакций, прочтения и typing требует WRITE. Новые `telos_key_`-ключи для транспортных маршрутов чата не поддерживаются. Чужой проект или объект возвращает 404. Cookie WebSocket требует допустимый Origin; секреты не передаются в URL.

## Слои и транзакции

`HTTP / WebSocket → ProjectChatService / ChatCommandsService → repositories → PostgreSQL`.

`dependencies/chat.py` отдаёт ресурсы lifespan и выполняет HTTP-авторизацию через короткий scope. `dependencies/scopes.py` собирает репозитории, AuthService и UnitOfWork для одной операции. В сервисах нет SQL и FastAPI, в репозиториях нет commit или сетевых вызовов.

Сообщение, ссылки, вложения и событие фиксируются одной транзакцией. Запись блокирует строку текущего чата: это упорядочивает события по `seq` и сериализует конкурентный повтор UUID. Идемпотентность имеет область `(chat_id, author_user_id, client_message_id)`. Правки проверяют `expected_revision`. Реакции задаются через `active`, поэтому повтор не переключает состояние обратно. Граница прочтения движется только вперёд.

Сокет не хранит AsyncSession. Авторизация, запись и resync открывают короткие области, которые завершаются до ожидания Redis или передачи ответа. HTTP-guard также освобождает соединение до открытия scope сценария, поэтому запрос не требует двух одновременных соединений. Защищённая выдача файла закрывает БД до FileResponse.

## Realtime и восстановление

`chat_events` — одновременно долговечный журнал дельты и transactional outbox. События содержат идентификаторы объектов, без копии текста переписки. Доставщик читает и гидратирует пакет, закрывает scope, публикует в `project_chat:{project_id}` и отдельной транзакцией отмечает доставку. Повторы при сбое или нескольких доставщиках допустимы: клиент применяет `seq` один раз.

Каждый процесс FastAPI держит локальные ограниченные очереди. Общий Redis Pub/Sub доставляет события другим процессам. Переполнение очереди закрывает медленный сокет с `1013`; остальные продолжают работу. При разрыве Redis-подписки приложение закрывает локальные сокеты, восстанавливает подписку и допускает reconnect. Готовность устанавливается после подтверждения подписки от Redis. Outbox остаётся в PostgreSQL.

После `ready` и reconnect клиент читает `GET .../events?after=cursor`. Дельта содержит также правки, удаления, реакции и изменения карточек. Новые WS-события временно буферизуются и применяются по порядку. Повтор истории не создаёт уведомления о старых сообщениях. Потеря ACK оставляет текст и UUID для ручного повтора, который возвращает уже сохранённое сообщение.

Периодического GET сообщений нет. HTTP нужен при открытии, подгрузке страниц, поиске, событии изменения счётчиков/карточек и восстановлении связи. Серверный outbox проверяется раз в 250 мс. Presence/typing живут только в Redis и не создают строки в PostgreSQL.

## HTTP API

Все пути ниже относительно `/api/v1/projects/{project_id}/chat`.

| Метод | Путь | Назначение |
|---|---|---|
| GET | пустой | Состав команды, unread, граница прочтения, курсор событий |
| GET | `/messages` | `before` / `after` по seq или `around` по ID сообщения, `limit` до 100 |
| GET | `/search?q=...` | Полнотекстовый поиск, `before`, `limit` |
| GET | `/events?after=...` | До 200 событий, `cursor` и `has_more` |
| GET | `/entities?q=...` | Picker объектов текущего проекта |
| POST | `/entities/resolve` | Чтение текущих карточек по списку до 100 ссылок |
| POST | `/messages` | Отправка с UUID |
| PATCH | `/messages/{id}` | Правка с `expected_revision` |
| DELETE | `/messages/{id}` | Мягкое удаление с `expected_revision` в JSON |
| PUT | `/messages/{id}/reaction` | `{ "reaction": "👍", "active": true }` |
| PUT | `/read` | `{ "message_id": 123 }` |
| POST | `/attachments` | Multipart `file`, защищённый черновик |
| DELETE | `/attachments/{uuid}` | Удаление своего неотправленного файла |
| GET | `/attachments/{uuid}/content` | Скачивание; `inline=true` для проверенных изображений |
| GET | `/attachments/{uuid}/preview` | Защищённая локальная JPEG-миниатюра, независимо от vision |

Карточки файлов используют общий вид с иконкой формата и миниатюрой изображения.
Для приватных загрузок Ариса выдача оригинала/миниатюры доступна только владельцу
диалога через `/aris/conversations/{id}/files/{uuid}/content` и `/preview`;
в проектном диалоге дополнительно проверяется текущий доступ к проекту.
Эти загрузки остаются приватными и не включаются автоматически в поиск проекта.

Write-пути REST и WS вызывают один `ChatCommandsService`, включая распределённые ограничения частоты.

## WebSocket API

Адрес: `/api/v1/projects/{project_id}/chat/ws`. Сервер присылает `ready` с `heartbeat_seconds`, `can_write`, списками `presence` и `typing`.

Пример команды:

```json
{
  "type": "message.send",
  "request_id": "91be3d5e-e910-4897-8845-039f50b59f26",
  "data": {
    "client_message_id": "380dc0f9-2fa0-437a-9938-19478b67f18f",
    "content": "Посмотрим критерии приёмки",
    "reply_to_message_id": null,
    "mentions": [2],
    "entities": [{ "entity_type": "TASK", "entity_id": 142 }],
    "attachment_ids": []
  }
}
```

Команды: `message.send`, `message.edit`, `message.delete`, `reaction.set`, `read.set`, `typing.started`, `typing.stopped`, `ping`. Для правки/удаления/реакции `message_id` находится в конверте рядом с `type`. ACK возвращает `request_id` и `data`; ошибка — `request_id`, `status`, `detail`. `ping` получает ACK с `pong: true`.

Постоянные события: `message.created`, `message.updated`, `message.deleted`, `reaction.updated`, `read.updated`, `entity.updated`, `entities.refresh`, `task.moved`, `member.changed`, `member.removed`. Формат — `type`, `project_id`, `seq`, `data`. Текущая read model сообщения находится в `data.message`. Временные `presence.updated` и `typing.updated` содержат `data.user_ids` и не имеют постоянного seq.

## Файлы, карточки и приватность

Файлы хранятся в отдельном каталоге `uploads/chat` через существующую атомарную файловую абстракцию. Storage key не выдаётся клиенту. Черновик виден только загрузившему участнику; после отправки файл видят участники проекта. Удаление сообщения закрывает выдачу его файлов. Проверяются имя, расширение, размер и сигнатуры изображений; MIME определяется сервером. Ответы используют `private, no-store`, `nosniff` и ограничивающий CSP.

Уборка удаляет неотправленные загрузки старше 24 часов и старые файлы без метаданных, включая остатки оборванных загрузок и удалённых проектов. Свежие файлы не затрагиваются. При редактировании сообщения набор его файлов сохраняется; новые вложения отправляются отдельным сообщением.

В ссылке на объект сохраняются тип и позиция. Для `DOCUMENT` идентичность задаётся
`document_ref` (Markdown, загрузка проекта или задачи), для остальных типов —
числовым `entity_id`; эти поля взаимоисключающие. Миграция сохраняет старые ссылки на Markdown. Заголовок, стадия/статус и адрес собираются из актуальных проектных данных. Изменения объектов создают события и обновляют открытые карточки; переименование стадии и ключа проекта вызывает пакетное обновление. Удалённый объект отображается как недоступный. Чужие объекты отклоняются до сохранения сообщения.

Таблицы чата исключены из knowledge pipeline. Отправка обычного сообщения не вызывает LLM, embeddings или Qdrant. Обращение к Арису ставит отдельное задание для AgentWorker и может вызвать модель и поиск по разрешённому проекту. В логах чата нет полного текста сообщений; ошибки валидации логируют только тип и расположение поля, без входного тела.

## Настройки и запуск

`docker compose up -d --build` поднимает также Redis. Nginx проксирует Upgrade WebSocket с сохранением порта Host. Локальный интерфейс: `http://localhost:5173`.

При запуске backend вне Docker сначала нужен `docker compose up -d redis`: порт Redis на компьютере — `127.0.0.1:6381`. В Compose адрес backend переопределён на `redis://redis:6379/0`. Redis обязателен: недоступность при старте завершает lifespan с ошибкой. Настройки перечислены в `backend/.env.example` и `ChatSettings`.

| Параметр | По умолчанию |
|---|---|
| `CHAT_QUEUE_SIZE` / `CHAT_MAX_CONNECTIONS` | 128 событий / 2000 сокетов на процесс |
| `CHAT_SEND_PER_MINUTE` / `CHAT_ACTIONS_PER_MINUTE` | 30 отправок / 120 постоянных действий на участника проекта |
| `CHAT_HEARTBEAT_SECONDS` / `CHAT_PRESENCE_TTL_SECONDS` | 20 / 60 секунд |
| `CHAT_TYPING_TTL_SECONDS` | 5 секунд; сигнал не чаще двух раз за 2 секунды |
| `CHAT_MAX_FRAME_BYTES` | 65536 байт |
| `CHAT_DRAFT_RETENTION_HOURS` / `CHAT_CLEANUP_SECONDS` | 24 часа / 3600 секунд |

Дополнительные границы: 8000 символов, 20 упоминаний, 10 карточек и 5 вложений на сообщение; файл до 10 МБ; до 20 неотправленных файлов на участника в чате.

При нескольких backend instances нужны общие PostgreSQL, Redis **и файловое хранилище** с одинаковыми storage keys. Готовый Compose запускает один backend; конфигурация нескольких процессов/реплик должна учитывать суммарный пул БД. Redis не хранит историю и не требует persistence для восстановления сообщений.

## Диагностика и проверки

Каждые 30 секунд `chat.metrics` пишет счётчики подключений/отключений, активные сокеты и очередь, переполнения, команды и ошибки, время записи сообщения, DB-scope и получения соединения, занятые/свободные соединения и ожидающие получения, публикации Redis, fan-out и ошибки файлов. Счётчики и суммы накопительные; частоты и среднее время вычисляются по разнице снимков. `chat.command` содержит project/actor/request/client-message ID, тип и длительность; `chat.message_created` также содержит chat/message ID. Метрики локальны процессу и сбрасываются при его перезапуске.

Автоматические проверки:

- PostgreSQL: lifecycle, rollback, membership, UUID-гонка, ревизии, soft delete/replies, FT search, курсоры, живые карточки и очистка файлов.
- Миграция: upgrade/downgrade, сравнение ORM/DDL, отсутствие backfill, сохранность проектов.
- HTTP: настоящая cookie/token-авторизация, READ scope, отзыв доступа, приватное скачивание без занятой БД, 12 конкурентных запросов при пуле из двух соединений.
- Redis/ASGI: fan-out двух runtimes, multi-tab presence, TTL, общие rate limits, неудача публикации и повтор outbox, медленный клиент, 12 idle sockets при пуле из двух соединений, серия из 24 сообщений, разрыв настоящей Pub/Sub-подписки и три волны переподключений.
- Frontend: транспорт/resync, merge ACK/WS/HTTP, безопасный Markdown; браузерные сценарии двух участников, reload, потерянный ACK, уведомления вне чата, picker/files, правки/удаление, поиск, scroll anchor, выбранная цитата, typing, отзыв доступа и клавиатура.

Это функциональные и ограниченные нагрузочные проверки, а не измерение предельной производительности сервера.

```powershell
cd backend
.\venv\Scripts\python.exe -m pytest -q
.\venv\Scripts\ruff.exe check src tests
cd ../frontend
npm run build
npm run lint
npm run test -- --run
$env:PLAYWRIGHT_CHANNEL='msedge'
npm run test:e2e
```

Проверка собранного локального Compose через настоящий Nginx/WebSocket создаёт двух временных пользователей и проект, затем удаляет их вместе с тестовым файлом:

```powershell
Get-Content backend/tests/smoke_chat_compose.py -Raw | docker compose exec -T backend python -
```
