# TELOS SPACE — спецификация визуального редизайна дашбордов

**Версия:** 1.0 · **Дата:** 14.11.2026

**Назначение:** инструкция для frontend-агента по максимально близкому воспроизведению согласованного макета для двух страниц: «Портфель» и «Обзор проекта».

**Статус:** референс следующей доработки; редизайн по этому документу ещё не реализован.

**Основной референс:** [dashboard-reference.png](dashboard-reference.png) (1536 × 1024).

**Интерфейс для сопоставления:** актуальные страницы запущенного приложения; старые снимки и их даты перечислены в [каталоге материалов](README.md).

**Источник цветов:** [дизайн-гайд](../DESIGN_GUIDE.md), [бренд](../BRAND_BRIEF.md) и [токены приложения](../../frontend/src/app.css). При расхождении с макетом приоритет имеет текущая тема TELOS SPACE; сине-чёрный фон картинки не переносится.

> **Важно:** изображение — визуальный референс, а не спецификация реальных данных и функций. Цифры, названия сторонних проектов, финансовые разделы, прогресс, даты и статусы, нарисованные генератором, не являются требованиями к API. Не добавлять вымышленные метрики или функциональность. **Не добавлять портрет Ариса:** в утверждённом варианте только маленький абстрактный знак/иконка.

## 1. Цель и критерии результата

Переработать исключительно визуальное представление существующих обзоров, сохранив навигацию, доступы, бизнес-логику, контракты API и расчёты. Обе страницы должны считываться «с первого взгляда»: основные показатели → проблемные зоны → ближайшие действия → краткий вывод Ариса. Не превращать интерфейс в яркую игровую панель: он должен оставаться рабочим инструментом с высокой плотностью информации и спокойной графитовой базой.

**Критерий приёмки:** при сравнении снимка готового приложения с референсом при ширине около 1536 px совпадают структура, пропорции, ритм отступов, высоты карточек, размер шрифтов, расположение акцентов, радиусы, рамки и графические элементы. Содержание берётся только из настоящих данных. Проводить визуальное сравнение по скриншотам после каждого этапа.

## 2. Дизайн-токены: строгая палитра

Использовать текущую тёмную тему приложения; **не заменять её сине-чёрным фоном макета**.

| Токен | Цвет | Назначение |
|---|---|---|
| `--ts-bg` | `#181818` | Основной фон |
| `--ts-workspace` | `#1F1F1F` | Рабочая область |
| `--ts-card` | `#252526` | Карточки |
| `--ts-card-raised` | `#2B2B2B` | Приподнятые/активные поверхности |
| `--ts-border` | `#3C3C3C` | Разделители и контуры |
| `--ts-text` | `#E8E8E8` | Основной текст |
| `--ts-muted` | `#CCCCCC` | Вторичный текст |
| `--ts-blue` | `#0078D4` | Основной синий |
| `--ts-blue-light` | `#4DAAFC` | Подсветка и ссылки |
| `--ts-violet` | `#9B8CFF` | Вторичный акцент, особенно Арис |

Семантические зелёный/красный/жёлтый для успеха, ошибки и предупреждения **брать из существующего дизайн-гайда приложения**: не вводить новые оттенки произвольно. Цвет никогда не должен быть единственным носителем смысла.

Градиенты — только в узких элементах (линия прогресса, подчёркивание активной вкладки, небольшая иконка, едва заметная подложка проекта); основной фон и большие карточки — нейтрально-графитовые. Максимально избегать неонового свечения и ярких декоративных пятен. Портреты, фигуры и лица в дашбордах запрещены.

Пример базовых CSS-токенов:

```css
:root {
  --ts-bg: #181818;
  --ts-workspace: #1f1f1f;
  --ts-card: #252526;
  --ts-card-raised: #2b2b2b;
  --ts-border: #3c3c3c;
  --ts-text: #e8e8e8;
  --ts-muted: #cccccc;
  --ts-blue: #0078d4;
  --ts-blue-light: #4daafc;
  --ts-violet: #9b8cff;
  --ts-radius-card: 12px;
  --ts-gap: 14px;
}
```

Не дублировать токены, если они уже есть в `app.css` или дизайн-системе; подключать существующие переменные и использовать этот список как карту соответствия.

## 3. Общая геометрия и типографика

- Макет-ориентир 1536×1024 содержит **две страницы рядом только для демонстрации**. В реальном приложении портфель и обзор проекта — **разные маршруты**, каждый занимает всю доступную ширину после боковой панели. Не создавать split-screen в продукте.
- Постоянная левая навигация сохраняется. На десктопе её ширина определяется существующим layout; не переписывать shell ради дашборда.
- Отступы от краёв рабочей области: 20–24 px; между секциями: 18–24 px; между карточками: 12–16 px; внутренние отступы карточек: 16–20 px.
- Карточки: радиус 10–12 px; тонкий контур 1 px; без тяжёлых теней. Допускается очень слабый верхний градиент на 1–2 тона в пределах серого.
- Типографика: Inter, системный fallback. Заголовок страницы 22–26 px / 600–700; заголовок карточки 14–16 px / 600; крупные KPI 26–32 px / 700; пояснения 11–13 px; основное содержимое 13–14 px. Не уменьшать основной текст ради точного совпадения с картинкой.
- Иконки: единый набор (например, уже используемый Lucide), единый stroke; не использовать emoji вместо UI-иконок.
- Числа выравнивать и по возможности применять `font-variant-numeric: tabular-nums`.
- На интерактивных элементах — заметные состояния hover, focus-visible, active; клавиатурная навигация обязательна.

## 4. Страница «Портфель» — структура сверху вниз

### 4.1. Заголовок и вкладки

Слева заголовок «Портфель» и краткая подпись; справа действие создания проекта. Под ним компактные вкладки **только из реально поддерживаемых представлений** (например, «Проекты» и «Сводка» из текущего UI). Активная вкладка отмечается короткой сине-фиолетовой или синей линией высотой 2 px. Не добавлять вкладки «Финансы», «Ресурсы», «Отчёты», если этих функций нет.

### 4.2. KPI-полоска

Четыре карточки в одну строку на широком экране: проекты в работе, задачи в работе, выполнено, просрочено. Если в текущем UI есть дополнительные проверенные показатели, их можно показать пятой карточкой, но не создавать фиктивные значения. В каждой карточке: маленькая иконка сверху, короткая подпись, крупное число, пояснение снизу. Просрочку выделять красным **только для значения и значка**, а не красным фоном всей карточки.

### 4.3. Прогресс и проблемные зоны

Две карточки рядом. Слева — «Фактический прогресс»: компактная кольцевая диаграмма (примерно 104–124 px), крупный процент в центре и рядом точные количества завершённых/открытых задач. Справа — «Требует внимания»: 2–4 наиболее значимых случая с коротким названием, контекстом проекта, сроком и кликабельным переходом. Если случаев нет, показывать позитивное пустое состояние.

**Важно:** процент завершённых задач не обозначать «прогрессом достижения цели проекта». Подписывать метрику как долю завершённых задач; любые иные показатели рассчитывать только при наличии утверждённой методики.

### 4.4. Карточки проектов

На широком экране — сетка из двух колонок. Каждая карточка содержит:

1. Иконку/логотип проекта 40–48 px с безопасным fallback.
2. Название и короткое описание в 1–2 строки.
3. Статус проекта с текстом и маленьким индикатором.
4. Тонкую полосу прогресса с процентом, если показатель действительно существует.
5. Нижнюю строку: количество задач, просрочки/риски и срок при наличии данных.

Карточка целиком открывает проект; дополнительные действия через отдельную кнопку с доступным именем. Не использовать декоративные звездочки, если избранное не поддерживается. Не заполнять сетку фальшивыми проектами, как на концепте.

### 4.5. «Вывод Ариса» — компактная панель

На странице портфеля это **небольшой горизонтальный блок**, без изображения человека: слева значок из 16–24 px в фирменном фиолетовом акценте, заголовок, одно-два предложения вывода, справа «Подробнее» и/или «Обновить разбор» (если функция уже реализована). Расширенный отчёт — по клику в существующей области или раскрытии. Длинные риски, выполненные работы и рекомендации **не выводить сразу полностью**.

Если разбор ещё не готов, устарел или не содержит подтверждённых данных, показывать соответствующее состояние; не имитировать актуальный вывод.

### 4.6. Недавние изменения

Сохранить существующий список в виде плотной, хорошо сканируемой ленты: маркер/иконка, код задачи, название, относительное время и статус. Не делать огромные карточки для каждого события. Учитывать длинные названия и доступность ссылок.

## 5. Страница «Обзор проекта» — структура сверху вниз

### 5.1. Шапка

Не заменять существующий глобальный header. Внутри проекта: название, ключ проекта, статус, строка короткого описания; логотип проекта 48–72 px становится основным визуальным акцентом. Его можно использовать для оформления локальной шапки без отдельной загрузки баннера, сохраняя текущий фон страницы и читаемость текста. Без пользовательского логотипа использовать существующую дефолтную иконку проекта; её дальнейший редизайн пока не согласован. В правой части — существующее действие «Открыть задачи». Текст шапки не встраивать в картинку. Не вводить новый финансовый hero-блок.

### 5.2. Навигация проекта

Сохранить реальные вкладки: обзор, чат, команда, канбан, задачи, календарь, структура, риски, доска, документы (согласно текущему интерфейсу и правам). Стилизовать активную вкладку тонким акцентным underline; не менять маршруты и порядок без причины.

### 5.3. Четыре KPI

«Всего задач», «Выполнено», «Просрочено», «Срок на неделе» — как в исходнике. Тот же визуальный язык, что в портфеле: спокойные карточки, числа крупно, цвет только в иконке/значении и короткой подписи.

### 5.4. Прогресс и стадии

Две карточки: слева кольцо «Фактический прогресс» и количества завершённых/открытых задач; справа «По стадиям» с горизонтальными полосами, числами и процентами. Сохранить **реальные названия стадий**, а не те, которые нарисованы в макете. Длина полосы отражает долю, а не вымышленную оценку готовности.

### 5.5. «Требует внимания» и «Следующие действия»

Две соседние карточки. Слева — компактный список просроченных задач, блокеров и важных рисков с приоритетом и сроком. Справа — структурированное отображение уже существующих данных: задачи без сроков, без исполнителей, контроль рисков и иные фактически поддерживаемые сигналы. Сохранять переходы к конкретным объектам.

### 5.6. «Вывод Ариса» — структурированный, но без портрета

Один широкий блок под основными операционными карточками:

- заголовок со **значком Ариса**, временем последнего разбора и действием обновления;
- **краткий тезис** на 1–3 строки: главный риск/состояние/следующий шаг;
- ниже — компактные разделы «Риски», «Что сделано», «Рекомендации», с максимум 2–3 элементами каждого типа в первичном отображении;
- «Показать полный разбор» раскрывает детальный текст, доказательства и ссылки на задачи/риски;
- если информация спорная, указывать ограничения и основание анализа.

**Запрет:** не использовать большой портрет, бюст, лицо, иллюстрацию человека или крупную декоративную AI-плашку. Максимум маленький геометрический символ рядом с названием.

### 5.7. Риски проекта и «О проекте»

Сохранить существующие секции ниже основного обзора, оформить теми же карточками, не убирать содержимое ради компактности. Допустимо свернуть длинные детали с сохранением доступности.

## 6. Графика: точное воспроизведение приоритетных элементов

**Приоритет 1:** геометрия карточек и сеток, размеры и отступы.

**Приоритет 2:** типографика, плотность текста, разделители, акцентные линии.

**Приоритет 3:** кольцевые диаграммы, тонкие progress bars, статусные точки, иконки.

**Приоритет 4:** едва заметные градиенты и подсветки — только после сверки с корпоративной палитрой.

Кольцевая диаграмма: SVG или уже используемая библиотека графиков; толщина кольца ~10–12 px; нейтральный трек, один акцентный сегмент; внутри крупное число и маленькая подпись. При 0% не показывать искусственный ненулевой сегмент. При отсутствии данных — «Нет данных», а не 0%.

Progress bar: высота 5–7 px, скруглённые края, нейтральный трек, заливка синяя либо с очень мягким переходом синий → фиолетовый. Для предупреждений — семантический цвет. Везде сохранять текстовое числовое значение.

Микроэффекты: hover-обводка/изменение фона 120–180 ms; без постоянного мерцания и анимаций. Учитывать `prefers-reduced-motion`.

## 7. Реализация в React

Предлагаемое разбиение (адаптировать к фактической структуре проекта):

```text
components/dashboard/
  DashboardCard.tsx
  MetricCard.tsx
  ProgressRing.tsx
  StageBars.tsx
  StatusPill.tsx
  AttentionList.tsx
  ProjectSummaryCard.tsx
  ArisInsightCompact.tsx
  ArisInsightDetailed.tsx
  RecentActivityList.tsx
pages/
  PortfolioOverview.tsx
  ProjectOverview.tsx
```

- Компоненты должны получать типизированные данные через props; не выполнять запросы в самих графических примитивах.
- Для портфеля и проекта переиспользовать одни и те же карточки и токены.
- Форматирование дат, процентов, количеств — централизованно, локаль `ru-RU`.
- Состояния `loading`, `empty`, `error`, `stale` и отсутствие доступа обязательны.
- Никаких моковых чисел в production JSX и никаких скрытых «улучшенных» метрик без источника данных.
- Изображения проектов загружать по разрешённым URL; предусмотреть fallback и обработку ошибок.

Пример минимальной основы карточки:

## 8. Доступность и адаптивность

- Заголовки должны иметь корректную иерархию, карточки — осмысленные названия.
- Для прогресс-диаграмм текстовое описание обязательно; не заставлять NVDA считывать SVG по частям.
- Кнопки и ссылки доступны с клавиатуры; `focus-visible` контрастный и не обрезан.
- Минимальная удобная область нажатия около 40–44 px, где возможно.
- Длинные названия задач не обрезать без возможности прочитать полностью.
- Контраст текста проверять по WCAG 2.2 AA; декоративные подсветки не должны ухудшать читаемость.
- На планшете карточки становятся одноколоночными по секциям; на телефоне — вертикальный поток без горизонтального скролла основной страницы.
- Для пользователя с уменьшенным масштабом/увеличенным шрифтом сохранять читаемость и порядок DOM.

## 9. План внедрения

1. Зафиксировать текущие маршруты, реальные API, показатели и поведение обеих страниц; сделать baseline-скриншоты.
2. Вынести общие токены и компоненты карточек без изменения данных.
3. Пересобрать портфель: KPI → прогресс/внимание → проекты → компактный Арис → события.
4. Пересобрать проект: шапка → KPI → прогресс/стадии → внимание/действия → подробный Арис → риски.
5. Добавить адаптивность, доступность, пустые состояния и проверки визуальных регрессий.
6. Сравнить снимки **реальных отдельных страниц** с соответствующими половинами референса, скорректировать пропорции и типографику; при этом не пытаться воспроизвести фальшивые данные.

## 10. Чек-лист приёмки

- [ ] Базовый фон — `#181818` / `#1F1F1F`, карточки — `#252526` / `#2B2B2B`, границы — `#3C3C3C`.
- [ ] Обе страницы визуально едины, не перегружены свечением.
- [ ] На дашбордах **нет изображения лица/портрета Ариса**.
