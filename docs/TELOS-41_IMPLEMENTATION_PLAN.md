**Без embeddings не означает без Ариса.** Существующая модель Ариса продолжает выбирать инструменты, читать код и отвечать с источниками. Запрещённый для этого этапа дополнительный объём — массовая или отложенная генерация описаний кода, semantic annotations, новые embedding/rerank-модели и векторный индекс Git. Уже работающий поиск знаний через Qdrant не отключать и не перенастраивать.

**Решение по размещению UI:** рабочее пространство находится в существующем разделе **«Знания → Код»**. Не добавлять верхнеуровневую вкладку проекта «Архитектура» или вторую «Код». В настройках проекта остаётся компактная карточка репозиториев: подключения, статусы индексации, управление и раскрываемая диагностика. Карта, поиск, длинный каталог и просмотр кода в настройках не остаются.

**Несколько репозиториев — базовый сценарий.** У каждого подключения собственные ref, observed/indexed SHA, права, ошибки и полнота. Общего SHA проекта нет. Нужны обзор всех доступных репозиториев и выбор конкретного; ошибка одного источника не должна скрывать остальные.

Работа с исходниками продукта — только чтение. Не добавлять редактирование Git-файлов, выполнение кода подключённого репозитория, запуск его тестов/CI, commit/push/merge или автоматическое закрытие задач. Это не запрещает агенту запускать тесты самой реализации TELOS в разрешённом локальном окружении.

## 4. Правила работы исполнителя и субагентов

- Начать с `git status --short` и относящегося к этапу diff. Два исходных вложения и этот план могут быть незакоммиченными пользовательскими файлами: не удалять и не перезаписывать их.
- Текущее поручение было на создание плана. Реализацию начинать только после отдельного поручения выполнить его. После такого поручения не переспрашивать разрешение на каждую обычную локальную правку.
- Скилы подключать по задаче: `dev-pipeline` для цикла работ; `fastapi-patterns` и нужные references для слоя backend; `frontend-design` для UI; `code-review` для итогового ревью. Правила проекта приоритетнее общих примеров скилов. Использовать только реально доступные скилы; не запускать Sites и не создавать внешнее демо вместо интерфейса репозитория.
- Общая реализация включает участки H: миграции, изоляцию и публикацию индекса. Агент на младшей модели может выполнять ограниченные этапы S/M; проектирование/ревью DDL, ACL и конкурентности передавать наиболее сильному доступному субагенту. Названия моделей зависят от среды, не выдумывать наличие `k3` или другого профиля.
- Один владелец этапа интегрирует изменения. Субагенту выдавать цель, точные файлы, контракт, запреты и приёмку; не давать всей истории без нужды. Не назначать двух авторов одного файла одновременно.
- Один ответ субагента должен содержать: изменённые файлы, результат, команды и статусы проверок, известные ограничения. Родитель просматривает diff и интеграционные стыки; сообщение субагента не заменяет проверку.
- Предлагаемые новые файлы не обязательны сами по себе. Сначала проверить, нет ли подходящего модуля. Не создавать пустой scaffolding, отдельную очередь, второй runtime, бессодержательные абстракции или тесты вызова каждого helper.
- После этапа обновить короткий статус в таблице раздела 6. Это единственный план; не создавать параллельные планы и отчёты в репозитории. Подробные логи/скриншоты держать в артефактах вне репозитория. Итоговые факты обновить в MEMORY, не вести там хронику.
- Различать `passed`, `failed`, `skipped`, `error`, `not_run`. Отсутствующий Docker, cookie или NVDA ограничивает конкретную приёмку; независимые работы продолжать. Не объявлять такую проверку пройденной.
- Commit, push, выкладка, изменение удалённых задач/комментариев и внешние сообщения не разрешены самим планом. Они требуют конкретного поручения. Не закрывать TELOS-41 автоматически.

Шаблон задания субагенту:

> Этап N, результат …; читать …; разрешено менять …; общий контракт …; не менять …; проверки …; вернуть diff/результат/ограничения. Нет права на commit/push/выкладку и изменение трекера.

## 5. Сквозные контракты, которые нельзя потерять

### 5.1. Идентичность и происхождение

- Источник: project + connection + provider repository ID + immutable commit SHA + path + точный диапазон. Для символа добавить qualified name/kind и версию экстрактора; не использовать голое имя как глобальный ключ.
- Файловый текст, добавленный контекст для поиска и пояснение интерфейса — разные поля. Нельзя выдавать добавленную сигнатуру/import за исходные строки файла.
- Строки 1-based inclusive; byte ranges и Unicode offsets различаются. Сохранить контракт существующего `read_file` и проверить конвертацию CRLF/Unicode при переходе к диапазону.
- Воспроизводимый просмотр фиксирует SHA; переключение ref в просмотрщике не меняет настройку подключения скрытно. История показывает только реально доступные версии; новый ref индексируется через существующее управляемое действие.
- Любой edge содержит тип, источник и уровень: `declared`, `resolved`, `candidate`, `unresolved`; будущий `inferred` не генерировать в TELOS-41. Containment отдельно от dependency; направление dependency — потребитель → зависимость.
- Межрепозиторный edge требует явного проверяемого основания. Совпадение имени модуля, пути или суффикса недостаточно. Не допускать ложных связей между тремя репозиториями с одинаковым `src/auth.py`.

### 5.2. Доступ, версии и индексация

- Все HTTP/MCP/Арис-чтения идут через общий сервис, текущие проектные права и внешний Git proof. Проверять доступ и перед выдачей/публикацией долгого результата. Кэш/счётчики/граф/история не раскрывают закрытые metadata.
- Индекс строится для закреплённого SHA. Переиспользование по hash не даёт доступа к чужому source; scope остаётся обязательным.
- Новое поколение экстрактора для того же SHA нельзя записывать поверх уже опубликованного снимка. До DDL определить identity производной версии и атомарный указатель на пригодное поколение.
- Публикация одного подключения сериализована; старый job не заменяет новый. При сбое сохраняется предыдущая пригодная версия с явным stale/partial. Готовность текста, символов и графа показывается раздельно.
- Меняется импортируемый файл или конфигурация разрешения — могут устареть связи в неизменившемся файле. Пересчитать затронутые связи либо явно поставить incomplete и запустить bounded продолжение.
- Не удерживать DB-сессию на время Git/LLM/парсинга. CPU-heavy разбор и layout вынести из event loop/UI thread.
- Миграции только поверх фактического Alembic head. Существующую БД обновлять после backup; тестировать DDL на отдельном real PostgreSQL. Не удалять volumes/uploads и не пересоздавать БД ради схемы. GC/автоматическое удаление старых snapshots не добавлять в этой задаче.

### 5.3. Интерфейс и несколько репозиториев

- Существующий внешний `view=code` сохранить; для внутреннего режима использовать отдельное имя, например `code_view`, чтобы не сломать «Карту» и «Историю» знаний.
- Единое состояние выбора: scope (все/connection), snapshot для каждого выбранного подключения, path/symbol/range, режим карты. URL хранит адресуемый выбор без секретов; Back/Forward и прямой переход восстанавливают контекст.
- Для «Все репозитории» показывать отдельные корни/группы и manifest версий. Не рисовать общий переключатель одной ветки или общий SHA. При открытии файла переходить к его connection/SHA. Репозитории загружать с пагинацией, не ограничиваться первой страницей из 20.

## 8. Матрица итоговой приёмки

Повторная сверка 25.11.2026 по исходному HTML подтвердила расхождения
первой версии с четырьмя концептами PDF: плоский каталог вместо дерева,
plain text и пустой центр, скрытые сведения, одинаковые узлы и поворот графа
вместо контейнеров слоёв. Прежние visible/count E2E этого не выявляли.

По уточнению пользователя в frontend 51ff8da файловый режим содержит одно
ленивое дерево слева и выбранный исходник справа. Дублирующий каталог удалён;
выбор repo/режимов/версии, статусы, метрики и inspector открываются в правом
Drawer через «Панель кода» рядом с вкладками знаний. Код и карты подняты сразу
под вкладки; исходник показан нативным статическим текстом с токенизацией,
доступным в полном объёме фрагмента через AX, без виртуализации. Исторический SHA отмечается
нейтрально; `stale` не называется неполнотой, пагинация и бинарные файлы не
показываются как ошибка. Настоящие пропуски каталога/ошибки чтения объясняются
отдельно. Сохранены реальные метрики. Monaco
включается при открытии файла, поддерживает номера и диапазоны строк,
копирование и GitHub; обычный текст остаётся fallback. Карты используют
карточки папок/файлов с иконками и подписями, раскрытие символов и группировку
по реальным путям. Каталог дополняет ограниченный срез графа: неизвестное
количество символов не превращается в ноль и не мешает пройти к исходнику.
Слои имеют контейнеры каталогов, radial — группы каталогов без пересечений.
Начальный масштаб 0,8–1 сохраняет корень и читаемость; явная команда «Вписать»
может уменьшить всю область. Широкая карта остаётся перемещаемой.

Скриншоты итоговой сборки просмотрены на desktop/mobile; автоматические
критерии геометрии, прокрутки и поведения перечислены в результатах этапов 6–8.
Это не означает совпадения макета по пикселям или ручной приёмки пользователя
на живом репозитории. Сохраняются «Знания → Код», несколько репозиториев,
нейтральные токены TELOS, реальные метрики и проверяемые связи. Backend-индекс,

## 9. Минимальный порядок первого рабочего захода

1. Восстановить границы из раздела 1, проверить `git status`, прочитать код/тесты этапа 0.
